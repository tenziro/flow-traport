## 1. 한 줄 요약

flow에 흩어진 수십 개 프로젝트에서 **"지금 내가 챙겨야 할 것"만 골라내는** 트래포트 사내 웹 대시보드. flow를 대체하지 않고, flow 위에 읽기 레이어와 최소한의 쓰기 액션을 얹는다.

## 2. 문제 정의

### 2.1 실측 근거

2026-07-27 기준 작성자 계정(`jongseok.lee@traport.com`)의 실제 flow 데이터:

| 지표                                   | 값       |
| -------------------------------------- | -------- |
| 참여 프로젝트                          | **59개** |
| 마감 임박 업무 (7일 내)                | 3건      |
| 마감 지남 + 최근 활동 (진짜 밀리는 것) | **11건** |
| 마감 지남 + 방치 (좀비)                | 3건      |
| 최근 14일 멘션                         | **28건** |

### 2.2 발견한 핵심 문제 두 가지

**발견 1 — 리스크는 프로젝트 단위로 집중된다.**

밀리는 업무 11건이 **전부 단 하나의 프로젝트**에서 나왔다. `[비즈플레이]B2603-삼성전기-출장예약 구축` 한 곳이다. 나머지 58개 프로젝트의 밀림은 0건.

즉, 59개 프로젝트를 나열하는 화면은 정보가 아니라 소음이다. 필요한 건 **"어느 프로젝트가 지금 타고 있는가"**를 위험도 순으로 보여주는 롤업이다.

**발견 2 — 알림은 절반이 중복이다.**

멘션 28건을 태스크 단위로 접으면 **고유 태스크 14개**로 줄어든다. 정확히 50% 감소.

| 태스크                       | 멘션 수 |
| ---------------------------- | ------- |
| Q004 보안이슈로 인한 DB 분리 | 5       |
| [공용복지몰] 출장예약플랫폼  | 5       |
| I001-보안이슈로 인한 DB 분리 | 3       |
| Q019 제휴숙소 팝업노출       | 3       |
| Q018 앱 및 간편결제 지원     | 2       |
| Q022 매핑코드                | 2       |
| 그 외 8건                    | 각 1    |

flow 기본 알림함은 이벤트를 시간순으로 흘려보낸다. 같은 태스크에서 다섯 번 불려도 다섯 줄이다. 스레드 단위로 접고 "마지막 발언자 + 미확인 건수"만 보여주면 확인 부담이 절반이 된다.

### 2.3 문제 진술

> 프로젝트 수가 수십 개를 넘어가면, flow의 프로젝트 중심 UI에서는 개인이 자기 리스크를 파악할 수 없다. 어느 프로젝트가 위험한지, 누가 나를 기다리는지 알려면 프로젝트를 하나씩 열어봐야 한다.

## 5. 아키텍처 결정

### 5.1 데이터 접근: flow REST API (`https://api.flow.team/user/*`)

**결정**: flow와 말하는 통로는 **REST 하나**다. 인증은 헤더 `x-flow-api-key`, 계약은
[api-spec.md](api-spec.md), 격리는 `lib/flow/` 어댑터 한 곳이다 — 화면 코드는 HTTP를 모른다.

> v0.1~v0.6은 MCP(`https://flow.team/ai/mcp`)였다. v4.0.0에서 전부 걷었다 — 무엇 위에 섰다가
> 왜 무너졌는지는 [§5.1.2](#512-전면-정정-2026-08-04-v400--mcp를-걷었다), 원문 기록은 이 절 끝의
> "폐기된 경로"다.

**화면 넷이 엔드포인트 하나 위에 선다.** 오늘·팀·리스크·내 업무가 전부
`GET /user/posts/projects/{projectId}/tasks/filter`다 (api-spec §6.1). 담당자 필터를 **서버가**
걸어 주고, 한 응답에 업무명·마감일·상태·담당자·등록자·등록일·수정일·우선순위가 같이 온다.
화면이 값 하나 더 그리자고 REST를 한 번 더 부르는 일이 없다 — 이 성질이 §5.1의 원가 계산을
지탱한다.

**타인 조회도 그 필터가 한다.** 담당자 컬럼(`COLUMN_SRNO 1`)에 남의 `userId`를 넣으면 그 사람
업무가 온다. 같은 컬럼에 레코드를 여러 개 주면 **OR**라서(실측 2026-08-04) 부서원 8명이
프로젝트당 **1회**다 — 팀 화면(§6.3)이 이 위에 섰다. 권한은 flow가 강제한다: 내가 멤버가 아닌
프로젝트는 애초에 목록에 없다. 대신 그 필터에 들어가는 `userId`는 **요청에서 받지 않는다**
(§8.1) — 받으면 그게 곧 유출 경로다.

**집계는 전부 우리 것이다.** `lib/aggregate/`가 유일한 판정자다 (§6.1.1). REST가 판정 재료
(`END_DT`·`EDTR_DTTM`·`optionCategory`)를 업무마다 주므로 분류 기준을 우리가 정하고, 같은
업무가 화면마다 다르게 분류될 여지가 없다.

**원가는 호출 수다 — 오늘 화면 한 번이 실측 81회, 상한은 분당 120회다** (api-spec §12).
견디는 장치는 셋이고 넷째는 없다.

| 장치 | 값 |
| --- | --- |
| 데이터 캐시 | 프로젝트 목록 600초, 업무 조회 **300초**. 오늘·내 업무는 **같은 URL**을 만들게 해서 캐시 한 칸을 나눠 쓴다 — 두 번째 화면은 0회다 |
| 동시성 | 프로젝트 훑기는 동시 10 |
| 실패 고지 | 429·권한으로 못 읽은 프로젝트는 **화면 아래에 이름으로 적는다** (`CollectNotice`). 조용히 빠져서 숫자가 적게 보이는 게 제일 나쁘다 ([BUG-040](bug-report.md#bug-040)) |

**REST가 못 하는 것** — 경로를 다 찔러 보고 접었다.

| 못 하는 것 | 실측 |
| --- | --- |
| 댓글 답글 **쓰기** | `POST …/replies/{commentId}`는 `404`고, 댓글 생성 Body에는 부모를 가리킬 자리가 없다 (api-spec §13.2). 앱은 `@이름`을 붙인 **일반 댓글**로 올린다. **읽기는 v4.2.0에 열렸다** — `?replyYn=Y` (api-spec §13.1) |
| 서버측 날짜 비교 | `IN` 외 연산자가 미공개다 (api-spec §11). 마감·수정일 판정은 전량을 받아 클라이언트에서 한다 |
| 업무 등록자의 부서·사진 | 이름까지만 온다. 사내 명단(§6.6)은 13명뿐이고 등록자 대부분이 타사 사용자다 (api-spec §6.1) |

---

**폐기된 경로 (v0.1~v0.6) — MCP.** 아래는 지우지 않고 남긴 기록이다. 근거가 어떻게 무너졌는지가
다음 결정의 재료다.

<details>
<summary>v0.3의 결정문과 그때의 근거</summary>

**결정**: Next.js 서버에서 flow MCP를 JSON-RPC로 호출한다. **REST API(`/user/*`)는 쓰지 않는다.**

> **v0.2에서 다시 뒤집힌 결정이다.** v0.1이 REST로 갈아탔으나, Phase 0 스파이크에서 REST를 택한 근거 다섯 중 넷이 실측으로 무너졌다. 아래는 전부 실제 호출로 확인한 값이다.

**v0.1의 근거가 어떻게 무너졌나**

| v0.1이 적은 근거                         | 실측 결과                                                                                                                                                      |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 표준 페이지네이션 `page`/`limit`/`meta`  | **틀림.** `cursor`/`pageSize` + `hasNext`/`lastCursor` (커서 방식). 게다가 MCP도 같은 커서를 그대로 노출한다 — "MCP는 불투명 커서"가 사실이 아니었다           |
| MCP는 read-only라 쓰기가 플랜에 종속     | **틀림.** 쓰기 도구 18종이 실제로 노출된다 (`flow_create_task` / `flow_update_task` / `flow_set_statuses` / `flow_create_comment` / `flow_mark_alarm_read` 등) |
| MCP 응답에 LLM용 마크다운이 섞인다       | **회피 가능.** 응답에 `structuredContent`가 따로 들어오고, 집계 도구는 `format:"structured"`로 마크다운을 생략한다                                             |
| Vercel serverless에서 세션 왕복이 비싸다 | **무시 가능.** `initialize`→`tools/call` 전체가 **59ms**, 세션 재사용 시 **11ms**. `notifications/initialized`는 생략해도 동작하므로 2왕복이면 된다            |
| 문서화된 계약                            | **유효.** MCP 쪽은 도구 설명이 계약의 전부다. REST 스펙([api-spec.md](api-spec.md))은 필드 의미를 읽는 참조 문서로 계속 쓴다                                   |

**결정적 이유는 따로 있다 — REST로는 전 직원 대시보드를 만들 수 없다.**

REST `/user/*`는 인증 주체 고정이다. 포털 스펙 변환기가 `userId` 파라미터를 제거하기 때문에([api-spec.md](api-spec.md) §0) **API 키 소유자 본인의 데이터만** 나온다. 반면 MCP `flow_get_my_worklist` 등은 `userId`를 받아 같은 회사 내 타인 조회가 되고, 이는 실제 호출로 확인했다. 즉 팀 화면(§6.3)이 REST에서는 구조적으로 불가능하다.

여기에 인증이 겹친다. **flow OAuth 토큰은 REST에서 거부되고 MCP에서만 통한다** (§5.2, R1). REST를 쓰려면 전 직원에게 개인 API 키 발급을 요구해야 하는데, 그건 §5.2가 애초에 피하려던 바로 그 UX다.

**얻는 것**: 집계 3종(`flow_get_my_worklist` / `flow_suggest_my_focus` / `flow_get_team_standup`)이 기성품이다. 작성자 계정으로 호출해 §2.1의 실측치(임박 3 / 밀림 11 / 방치 3 / 멘션 28)가 그대로 재현되는 것을 확인했다.

**대가**: 계약이 도구 설명문에 흩어져 있어 REST 스펙만큼 정밀하지 않다. 응답 스키마는 런타임 검증으로 방어한다.

**우리 집계 로직을 버리지 않는 이유**: `lib/aggregate/`는 그대로 둔다. MCP 집계는 가중치를 우리가 통제할 수 없고(§12 Q5), 리스크 보드(§6.2)의 프로젝트 위험도 점수는 MCP에 대응 도구가 없다. MCP 집계는 교차 검증용으로도 쓴다.

**격리**: 모든 flow 호출은 `lib/flow/` 어댑터 한 곳에 가둔다. 화면 코드는 MCP도 JSON-RPC도 모른다.

#### 5.1.1 정정 (v0.5) — REST 배제 근거 절반이 사라졌다. 그래도 이관은 안 한다

위 "REST는 쓰지 않는다"는 이제 사실과 다르다. REST는 이미 세 경로에서 돌고 있고([rest.ts](../src/lib/flow/rest.ts)), v0.13.0에서 **개인 API 키를 필수로 받기 시작하면서(§5.2 정정) REST 배제 근거 중 하나가 통째로 소멸했다.** 정리하면:

| 배제 근거였던 것                                        | 2026-07-28 현재                                                                                      |
| ------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| REST는 전 직원에게 개인 API 키 발급을 요구한다 → 도입 죽음 | **소멸.** v0.13.0부터 로그인에 개인 키가 **필수**다. 비용은 이미 냈다. 안 쓰면 낸 값만 버리는 셈이다 |
| OAuth 토큰이 REST에서 400 (audience 불일치)             | 유효하지만 무의미해졌다. REST는 개인 API 키로 간다 — 토큰을 쓸 이유가 없다                             |
| `/user/*` 는 인증 주체 고정이라 타인 조회 불가            | **부분적으로 틀렸다** ([아래 정정](#511-정정-2026-07-31)). 막는 건 권한이 아니라 호출 원가다             |
| MCP 집계 3종이 기성품                                   | 유효. 아래 원가 계산 참고                                                                            |

**그래서 결론은 "REST로 이관"이 아니라 하이브리드 확정이다.**

- **MCP** = 집계와 타인 조회. `flow_get_my_worklist` · `flow_suggest_my_focus` · `flow_get_team_standup`. 이 셋은 REST에 대응물이 없다
- **REST** = MCP가 못 하거나 깨진 것. 지금 세 경로 + §13의 확장 후보

**이관 원가 — 워크리스트 한 화면을 REST로 재현하면 178회다**

| 단계                                        | 호출 수                                      |
| ------------------------------------------- | -------------------------------------------- |
| `GET /user/projects`                        | 1 (59개)                                     |
| `GET /user/projects/{id}/columns`           | 59 — 마감일·상태 컬럼의 `columnSrno` 해소용  |
| `GET /user/projects/{id}/columns/status`    | 59 — `optionSrno` → 상태명                   |
| `GET .../tasks/filter?pageSize=100`         | 59 ~ 350 (한 프로젝트 600건+ 실측 = 6페이지) |
| **합계**                                    | **178 ~ 470회** (DB가 없어 요청마다 반복)    |
| MCP `flow_get_my_worklist`                  | **1회**                                      |

레이트 리밋 임계값은 비공개다(api-spec §11). 집계를 REST로 옮기는 건 **선택지가 아니다.**

**REST가 이기는 지점은 따로 있다 — 세밀함이다.** MCP 집계는 가중치·필터를 우리가 못 건드리고 응답 필드가 고정이다. REST는 단일 필드 수정 엔드포인트(마감일·우선순위·담당자), 알림 읽음 처리, 전체 댓글 스레드, 필터 조합(`filters=WORKER`)을 준다. 전부 지금 화면에 **없는** 것이고, MCP에는 길이 없다. §13이 그 목록이다.

#### 5.1.1 정정 (2026-07-31)

**전면 대체는 손해다. 하이브리드를 유지하되 MCP 도구 둘은 걷어낸다.**

살아 있는 MCP 호출 지점은 일곱 곳(도구 9종)이다. 하나씩 REST로 옮겨 보고 셋으로 갈랐다.

| `flow_get_my_profile` (로그인)                               | **못 옮긴다.** 세션을 만드는 유일한 경로다. 아래 ①                                                                                                |

**① 신원이 사라진다 — 이게 원가보다 크다.** OAuth 토큰은 REST에서 400이고(§5.2), REST를 API 키로
부르면 `/user/employees/me`는 **키 소유자**를 돌려준다. MCP를 걷으면 "로그인한 사람"이라는 개념이
없어지고 **키를 붙여넣은 사람이 곧 신원**이 된다. 지금은 OAuth가 신원을 잡고 키는 데이터 통로일
뿐이라 두 겹이고, `mergeMentionComments`·`taskNews`의 `receiverId` 대조가 그 위에 서 있다 (§8.1).
`@traport.com` 도메인 검증도 이 프로필에서 온다.

**② 원가는 추정이 아니라 실증됐다.** 위 표의 178~470회는 계산이었는데, v1.2.0 내 업무 화면이
정확히 그 방식(프로젝트당 `tasks/filter`)으로 만들어졌고 **분당 120회 중 60회**를 쓴다 (§6.5).
오늘 화면을 같은 방식으로 옮기면 그 위에 또 60회 + 컬럼·상태 해소가 붙는다 — 한 사람이 두 화면을
연달아 열면 상한을 넘는다. MCP엔 그 상한이 없고 왕복은 11~59ms다.

**③ 타인 조회 표현을 바로잡는다.** 위 표의 "`/user/*`는 타인 조회 불가"는 이제 부정확하다.
`tasks/filter`의 `WORKER` 필터에 남의 `userId`를 넣으면 그 사람 업무가 나오고(그래서 §8.1이
세션에서만 채우게 막는다), `calendars/events?userId=`도 열려 있다. 팀 화면을 막는 건 **권한이
아니라 산수**다 — `tasks/filter`가 프로젝트 단위라 부서원 6명 × 프로젝트 59개 = 354회다.

#### 5.1.2 전면 정정 (2026-08-04, v4.0.0) — **MCP를 걷었다**

**§5.1과 §5.1.1의 결론이 뒤집혔다. 지금 데이터 경로는 REST 하나다** (`https://api.flow.team`,
`x-flow-api-key`). MCP 코드·설정·의존성은 전부 지웠다.

§5.1.1이 "못 옮긴다"고 적은 셋을 다시 봤고, 막고 있던 산수가 실은 **틀린 전제** 위에 있었다.

| §5.1.1이 막았던 것 | 어떻게 풀렸나 |
| --- | --- |
| 팀 스탠드업 = 부서원 8명 × 프로젝트 59개 = **472회** | **59회다.** `filterRecords`에 같은 `COLUMN_SRNO`로 레코드를 여러 개 주면 **OR**로 걸린다 (실측 2026-08-04, api-spec §6.1). 8명을 한 요청에 담아 프로젝트당 1회로 끝난다 |
| 오늘 + 내 업무를 연달아 열면 상한(분당 120)을 넘는다 | **같은 URL이라 캐시 한 칸을 나눠 쓴다.** 두 화면이 `listWorkerTasks(projectId, [나])`로 완전히 같은 요청을 만들고, 거기에 **300초** 데이터 캐시를 건다. 두 번째 화면은 0회다 |
| 포커스의 마지막 댓글은 업무당 REST 2회 | **1회다.** `tasks/filter` 응답에 `postId`가 이미 있어서 `resolvePostId`가 필요 없다. 게다가 상위 8건만 본다 |
| 신원이 사라진다 (①) | **맞는 지적이었고, 그대로 받아들였다.** OAuth를 버리고 **개인 API 키가 곧 신원**이다 — 아래 §5.2.1 |

**MCP를 걷어서 얻은 것** (호출 수를 줄이려던 게 아니다):

- **방치 업무에 창의 상한이 없어졌다.** MCP 워크리스트는 방치를 **건수만** 주고 목록을 안 줘서,
  활동 창을 180일로 넓혀 한 번 더 부르는 우회를 썼다. 그래도 180일이 그 도구의 상한이라 그보다
  오래된 건 영영 목록으로 못 왔다 (§12 Q10). REST는 업무마다 `EDTR_DTTM`(마지막 수정)을 주므로
  우리가 직접 가른다 — 이제 건수와 목록이 항상 맞는다.
- **집계 가중치가 우리 것이 됐다.** `lib/aggregate/`가 유일한 판정자다. 같은 업무가 화면마다
  다른 기준으로 분류되던 여지가 사라졌다.
- **등록자·등록일이 모든 화면에 있다.** 셋을 MCP로 만들던 화면(오늘·팀·리스크)에 없던 값이
  추가 호출 없이 붙었다 (api-spec §6.1).
- **계약이 문서가 됐다.** MCP는 도구 설명이 계약의 전부였다(§10 R3). 이제 [api-spec.md](api-spec.md)가
  단일 계약이다.

**대가는 호출 수와 그 결과다.** 오늘 화면 한 번이 실측 **81회**다 (api-spec §12). 분당 120회
안에는 들어가지만 여유가 없어서, 상한에 걸린 프로젝트는 **화면에 이름으로 적는다**
(`collectTasks`의 `failed`) — 조용히 빠져서 숫자가 적게 보이는 것보다 낫다.

### 5.2 인증: 개인 flow API 키 하나

**결정**: 로그인은 **자기 flow API 키를 한 번 붙여넣는 것**이다. 그 키가 데이터 통로이자 신원이다.

| 무엇 | 어디에 |
| --- | --- |
| 신원 | 그 키로 부른 `GET /user/employees/me` (api-spec §3.1). `userId`·`fullname`·부서명이 **세션 쿠키**(7일, AES-256-GCM 봉인, httpOnly)에 들어간다 |
| 키 자체 | 별도 봉인 쿠키 `fc_key`(1년, httpOnly). 세션(7일)에 담으면 만료마다 다시 물어야 한다 |
| 검증 | 저장 전에 `GET /user/projects` 1회. 키 값은 **메시지에도 로그에도 남기지 않는다** (§8.1) |
| 회사 판정 | 이메일 도메인 `@traport.com`. 아니면 거부 |
| 발급 | 로그인 화면에 링크를 둔다 — `https://api.flow.team/account/api-keys` |

**자체 권한 모델을 만들지 않는다.** 권한은 flow가 강제한다 — 사용자가 멤버가 아닌 프로젝트는
API로도 안 보인다 (flow 문서: _"마스터키는 권한을 확대하지 않습니다"_).

**대가는 둘이다.** ① 도입이 "버튼 하나"가 아니라 한 사람당 링크 한 번 + 붙여넣기 한 번이다.
② **키가 곧 사람**이라 신원이 한 겹이다. 그래서 §8.1이 유일한 방어선이 된다 — 담당자 필터에
들어가는 `userId`는 세션이나 부서 명단에서만 채운다.

**폐기된 경로 (v0.1~v0.6) — flow OAuth 2.1.** 무너진 지점은 [§5.2.1](#521-정정-2026-08-04-v400--oauth를-걷었다-로그인은-개인-api-키-하나다)이고,
아래가 그때의 실측 기록이다.

<details>
<summary>OAuth 서버 스펙과 R1 실측 (토큰은 MCP에서만 통했다)</summary>

**결정**: 사용자마다 자기 flow 계정으로 OAuth 로그인. 액세스 토큰으로 **MCP를** 호출한다.

**이게 왜 중요한가**: REST 문서의 기본 인증은 `x-flow-api-key`이고, 이 키는 개인이 flow에서 직접 발급받아야 한다. 전 직원에게 "flow 가서 API 키 발급받아 붙여넣으세요"를 요구하면 도입이 죽는다. OAuth가 되면 **"flow로 로그인" 버튼 하나**로 끝난다.

확인된 flow OAuth 서버 스펙:

```
Authorization Server : https://flow-oauth-worker.flow-auth.workers.dev
  authorization_endpoint : /authorize
  token_endpoint         : /token
  registration_endpoint  : /register     ← Dynamic Client Registration 지원 (실제 등록 성공, 201)
  grant_types            : authorization_code, refresh_token
  code_challenge_methods : S256          ← PKCE
  scopes                 : user
  token_endpoint_auth    : client_secret_basic / client_secret_post / none
```

**실측: 토큰은 MCP에서만 통한다 (R1 해소)**

AS는 **RFC 8707 `resource` 파라미터를 필수로 요구**하고, 값으로 **등록된 MCP 서버만** 받는다. `authorize`와 `token` 양쪽에 모두 실어야 한다.

```
resource 누락                        → invalid_request  "resource parameter is required (RFC 8707)"
resource=https://api.flow.team       → invalid_target   "resource is not a registered MCP server"
resource=https://flow.team/ai/mcp    → 200 access_token (expires_in 3600, refresh_token 있음)
```

발급받은 토큰으로:

```
POST https://flow.team/ai/mcp  tools/call flow_get_my_profile  → 200  {"userId":"jongseok.lee@traport.com","fullname":"이종석",…}
GET  https://api.flow.team/user/employees/me                   → 400  INVALID_REQUEST "올바르지 않은 OAuth 인증 요청입니다"
```

MCP가 200을 주는 대조군이 있으므로 REST의 400은 토큰 문제가 아니라 **audience 불일치**다. REST는 OAuth로 갈 수 없다 — §5.1의 결론이 여기서 나온다.

**위임이 실제로 성립한다**: `flow_get_my_profile`이 API Key 소유자가 아니라 **로그인한 사람**을 반환했다. 즉 MCP 호출은 사용자 위임으로 동작한다.

**설계**

- 서버가 confidential client로 DCR 1회 등록 → `client_id` / `client_secret` (완료)
- 로그인 = Authorization Code + PKCE(S256) + `resource=https://flow.team/ai/mcp`
- 토큰은 **브라우저에 절대 노출하지 않는다.** 암호화 쿠키 세션에만
- 권한은 flow가 강제한다. 사용자가 멤버가 아닌 프로젝트는 API로도 안 보인다 (flow 문서: _"마스터키는 권한을 확대하지 않습니다"_). **자체 권한 모델을 만들지 않는다.**
- 로그인 후 소속 회사가 트래포트인지 확인. 아니면 거부

**트래포트 확인 방법**: MCP `flow_get_my_profile`은 `inttId`(회사 식별자)를 주지 않는다. 프로필의 **이메일 도메인이 `@traport.com`인지**로 판정한다. 회사 식별자는 REST 프로필이 주는 `BFLOW_300022998467`이지만, REST는 위 이유로 쓰지 않는다.

**정정 (v0.13.0): "버튼 하나"가 되지 않았다 — 개인 API 키를 한 번 받는다.**

위에서 "전 직원에게 API 키 발급을 요구하면 도입이 죽는다"고 적었고 그 판단 자체는 유효하다. 그런데 MCP만으로 화면이 서지 않았다. 멘션 **댓글 본문**과 `taskSrno`→`postId` 해소는 MCP에 길이 없어 REST를 쓰는데(§5.1 마지막, [rest.ts](../src/lib/flow/rest.ts) 주석), REST는 `x-flow-api-key` 하나뿐이고 그 키는 **소유자 한 명** 기준이다. 공용 키 하나로 돌리면 다른 사람이 로그인했을 때 멘션 본문이 비고 댓글이 막히고, 소유자의 프로젝트 제목 59개가 응답 페이로드에 실린다.

그래서 **로그인 버튼을 누르면 최초 1회 개인 키를 받는다.** 키가 자기 것이면 REST 세 경로가 모두 자기 기준으로 돈다.

- 받는 시점은 OAuth **전**이다. 그래서 세션이 아니라 별도 봉인 쿠키(`fc_key`, 1년, httpOnly)에 넣는다 — 세션(7일)에 담으면 만료마다 다시 물어야 한다.
- **필수다.** 건너뛰면 반쪽으로 선 화면에 로그인되는데 사용자는 원인을 못 찾는다. 화면(모달)과 `/api/auth/login` 양쪽에서 막는다.
- 저장 전에 `/user/projects` 1회로 검증한다. 키 값은 메시지에도 로그에도 남기지 않는다 (§8.1).
- 발급 링크를 로그인 화면과 모달 양쪽에 둔다 (`https://api.flow.team/account/api-keys`).

도입 비용은 **한 사람당 한 번, 링크 한 번 + 붙여넣기 한 번**이다. "버튼 하나"보다는 무겁지만 반쪽 화면보다는 낫다는 판단이다.

</details>

#### 5.2.1 정정 (2026-08-04, v4.0.0) — **OAuth를 걷었다. 로그인은 개인 API 키 하나다**

§5.1.2로 MCP가 없어지면서 **OAuth 토큰이 쓸 데가 없어졌다.** 그 토큰은 MCP에서만 통했고
(위 R1 실측), REST는 `x-flow-api-key`만 받는다. 토큰을 신원 확인에라도 쓰려 했지만
**AS에 userinfo 엔드포인트가 없다** — 토큰을 사람 이름으로 바꿔 주던 유일한 길이
`flow_get_my_profile`, 즉 MCP였다.

그래서 신원도 키가 잡는다:

- 로그인 = **개인 API 키 한 번 붙여넣기**. `/api/auth/login`·`/api/auth/callback` 두 라우트와
  PKCE 코드는 지웠다.
- 신원 = 그 키로 부른 `GET /user/employees/me` (api-spec §3.1). `userId`·`fullname`·부서명이
  세션 쿠키에 들어간다.
- 트래포트 판정은 그대로 **이메일 도메인 `@traport.com`** 이다.
- **키가 곧 사람이라는 뜻**이라 §8.1의 방어선이 더 중요해졌다: 담당자 필터에 들어가는
  `userId`는 세션이나 부서 명단에서만 채운다. 요청에서 받은 값을 넘기면 그게 유출 경로다.

§5.1.1 ①이 걱정한 "키를 붙여넣은 사람이 곧 신원"이 실제로 그렇게 됐다. 두 겹이 한 겹이 된
건 손실이 맞지만, 그 한 겹은 flow가 발급하고 flow가 폐기할 수 있는 자격이다 — 우리가 따로
검증할 게 없다.

### 5.3 저장소: 없음

**결정**: 데이터베이스를 두지 않는다. Supabase도 쓰지 않는다.

| 필요           | 수단                                                | DB가 필요 없는 이유                                      |
| -------------- | --------------------------------------------------- | -------------------------------------------------------- |
| 세션 / API 키  | 암호화 쿠키 (`iron-session`)                        | stateless. Vercel serverless에 적합                      |
| 집계 캐시      | Vercel Data Cache (`unstable_cache` + `revalidate`) | 인스턴스 간 공유됨. in-memory와 달리 serverless에서 동작 |
| 알림 읽음 상태 | `PATCH /user/alarms/read` (api-spec §7.2)           | **flow에 이미 있다**                                     |
| 쓰기 감사 로그 | flow에 그대로 기록됨                                | 별도 불필요                                              |

v1에 flow 밖에 저장할 상태가 하나도 없다. 생기면 그때 도입한다.

### 5.4 스택 / 배포

Next.js (App Router) + TypeScript + Tailwind CSS. **Vercel 배포.**

접근 제어는 네트워크가 아니라 개인 API 키로 한다 (§5.2) — 키가 없으면 아무 데이터도 없다. `robots: noindex`.

> 상태·마감일·우선순위·담당자 바꾸기(§6.1.4), 댓글이 모달로 들어갔다. 모달은 표마다
> **하나**다. 줄마다 두면 열 줄에 모달 열 개가 DOM에 깔린다. 점수·이유는 포커스 응답에만
> 있어서(§6.1.3) 다른 표의 모달에서는 그 자리를 안 그린다 — 0으로 채우지 않는다. 순위

> 닿는 선으로 가른다. **업무명 아래 딱지 줄은 마감 D-DAY · 등록자 · 포커스 순위다 (v3.1.2)**
> — 표에서 넘어온 값을 그대로 얹는 자리다. 등록자가 여기인 것은 이 값만 어디서도 바꿀 수
> 없어서 아래 다섯 줄(고치는 자리)에 낄 이유가 없기 때문이다. 상태 배지는 여기 두지 않는다:
> `상태` 줄이 같은 값을 같은 배지로 이미 보여준다.
>
> **상태 필터는 표가 스스로 한다.** 표 위 칩을 누르면 그 자리에서 걸러진다 — URL도 서버
> 왕복도 없다(v2.0.0에 `?focus=`/`?overdue=`를 지웠다. 951줄 화면을 서버로 다녀오면 실측
> 7초다 — §6.5). 칩은 데이터에 실제로 있는 상태만, 그리고 **두 종류 이상일 때만** 낸다 —
> flow 커스텀 상태라 고정 목록을 그리면 0건짜리 칩이 늘어선다. 필터는 표만 줄이고 위
> KPI·분포 막대는 전체를 유지한다.

#### 6.1.1 집계 규칙 (`lib/aggregate/classifyTasks`가 수행)

| 분류          | 정의                                  |
| ------------- | ------------------------------------- |
| 임박          | 마감 ≤ +7일, 미완료                   |
| 밀림 (active) | 마감 < 오늘 **AND** 최근 30일 내 활동 |
| 방치 (stale)  | 마감 < 오늘 **AND** 30일 무활동       |

밀림과 방치를 나누는 게 핵심이다. 섞으면 액션 리스트가 죽은 업무로 오염된다.

> **구현 결과 (v0.4)**: 이 분류는 `flow_get_my_worklist`가 이미 같은 규칙(`imminentDays` 7 / `overdueActiveDays` 30 기본값)으로 해서 준다. `lib/aggregate/classifyTasks`는 오늘 화면에서 쓰지 않는다 — worklist 응답에 `progress`·`lastActivityAt`이 없어 재분류할 재료 자체가 없다. 우리가 직접 하는 집계는 멘션 접기(§6.1.2) 하나뿐이다.
>
> **정정 (v4.0.0)**: 그 도구가 없어졌고 **`classifyTasks`가 네 화면 전부의 유일한 판정자**가
> 됐다. `tasks/filter`가 업무마다 `END_DT`(마감)와 `EDTR_DTTM`(마지막 수정)을 줘서 재료가
> 생겼다. 규칙 자체는 위 표 그대로다 — 같은 값이 나오는지는 실측으로 대조했다
> (임박 1 · 밀림 7 · 방치 12 · 그 외 926, 업무 946건).

#### 6.1.2 멘션 접기 (핵심 차별점)

동일 태스크의 알림을 한 행으로 병합한다. 병합 키는 알림이 가리키는 **`link`**다 — flow 알림은 `taskId`를 주지 않는다 (REST 원본도 마찬가지: [api-spec.md](api-spec.md) §7.1). 대신 대상 URL을 `link`로 준다.

> **소스 교체 (v0.4)**: `flow_list_alarms`는 서버측 스키마 검증에서 죽는다 (`message`/`alarmType`이 null → `TOOL_EXECUTION_FAILED`, [bug-report.md](bug-report.md) BUG-001). 같은 멘션을 `flow_get_my_worklist.mentions`가 `{from, title, at, link}`로 그대로 준다 — 이쪽을 쓴다. 읽음 처리(Phase 2)만 `flow_mark_alarm_read`가 필요한데, 알림 목록 없이 되는지는 그때 확인한다.

```
Q004 보안이슈로 인한 DB 분리          [5건 · 최근 ymh0510 · 오늘 11:00]   [읽음]
[공용복지몰] 출장예약플랫폼            [5건 · 최근 ymh0510 · 07-14]        [읽음]
I001-보안이슈로 인한 DB 분리          [3건 · 최근 ymh0510 · 07-15]        [읽음]
```

- 정렬: 최근 알림 시각 내림차순
- 행 펼침 시 개별 알림 타임라인
- **읽음 처리**: `flow_mark_alarm_read` — 접힌 행 전체를 한 번에
- **검증 기준**: 작성자 계정 기준 28건 → 14행 (**실측으로 재현됨**, §11 Phase 0)

> **상세 모달이 열리면서 스레드 전량을 편다 (v4.2.0)**. 전에는 나를 부른 알림 두어 줄이
> 기본이고 `댓글 다 보기`를 눌러야 나머지가 나왔는데, **불린 이유는 대개 그 앞뒤 말에 있다** —
> 맥락 없는 두 줄이 기본 화면이면 결국 매번 한 번 더 눌러야 한다. 열 때 REST 한 번이고,
> 모달은 사람 손으로 여니 분당 상한(120)에 닿지 않는다.
>
> | 결정 | 이유 |
> | --- | --- |
> | **나를 부른 줄만 면·아이콘 색을 올린다** | 스무 줄을 한 번에 펴면 내가 불린 자리가 묻힌다. **업무 상세 모달도 같다** — 스레드가 길수록 내가 답할 자리를 찾기 어렵다 |
> | 판정은 **본문의 멘션 마크업**이다 (`mentionsMe`) | `@[이종석](jongseok.lee@traport.com)`의 괄호 안이 곧 세션의 `userId`다. 알림으로 맞추면 알림 창(최근 7일·12건)을 벗어난 옛 멘션이 강조에서 빠지고, flow가 남의 이름으로 보내면서 **내가 쓴 줄**을 가리키는 알림까지 따라 들어온다 (실측 8건 중 1건 — api-spec §7.1). 이름은 안 본다 — 동명이인이 있고 전원 호출(`@[ALL](ALL)`)은 id가 `ALL`이라 안 걸린다 |
> | 시스템 기록은 **강조하지 않는다** | 담당자로 내 이름이 박힌 변경 기록까지 `나를 부름`이 된다 |
> | 색 말고 **`나를 부름` 글자도 붙인다** | 면과 아이콘 색만으로는 색을 못 가리는 사람에게 아무 표시가 없다 |
> | 오는 동안은 **골격**이다 (`CommentRowsSkeleton`) | 알림 목록을 먼저 그렸다가 댓글로 갈아 끼우면 같은 말이 자리를 옮겨 다시 서서, 읽던 줄을 눈으로 다시 찾아야 한다. 줄 수는 알림 건수(최대 4)라 도착했을 때 높이가 덜 튄다 |
> | 못 가져오면 **알림 목록으로 돌아간다** | 알림은 이미 손에 있어서 공짜다. 스레드 한 번 실패했다고 모달이 비면 표에서 보이던 것보다 못한 화면이 된다 |
> | `댓글 다 보기` 단추를 없앴다 | 열 때 이미 편다. 남겨 두면 눌러도 아무 일이 없는 단추다 |

#### 6.1.3 포커스 스코어링

가중 신호: 마감 긴박도 · 최근 멘션/댓글 수(열기) · 우선순위 · 진행률(마무리각).

가중치는 코드 상수 하나로 시작한다. 사용자 설정 UI는 만들지 않는다 (§12 Q5).

각 업무 행에서 화면 이탈 없이:

**전부 REST다 (v4.0.0)** — 예전에는 앞 셋이 MCP 쓰기 도구였다.

| 담당자 | REST `PATCH .../tasks/{id}/worker` | `변경` → 고르기 모달 → `확인` | 구현 (§13 A4)  |

> **편집 패널 (v0.15)**: 상태·마감일·우선순위·담당자 네 줄을 한 장에 세웠다. 라벨 폭을 고정해
> 컨트롤 왼쪽 경계를 맞췄다 — 줄마다 시작점이 다르면 네 줄이 네 카드처럼 읽힌다. 마감일은
> `<input type="date">`에서 shadcn Calendar + Popover로 바꿨다 (브라우저마다 다른 UI가 화면
> 안에서 유일하게 튀었다). **현재 값은 패널을 열 때 REST로 가져온다** — 워크리스트 응답에
> 우선순위·담당자가 없어서, 목록을 그릴 때 업무 수만큼 부르면 원가 계산에 걸린다.
>
> `updateTaskWorker`는 담당자를 **덮어쓴다** (한 명으로). REST가 배열 추가/제거를 안 나눠서
> 여럿을 유지하려면 flow에서 해야 한다 — 패널에 그렇게 적어 뒀다.

> **바꾸기 모달 (v0.20)**: 위 편집 패널을 **모달**로 올리고, **읽는 자리와 고치는 자리를 갈랐다.**
>
> v0.15까지는 셀렉트 네 개가 행 안에 펼쳐져 있고 지금 값이 그 셀렉트의 placeholder(`지금 진행중`)
> 였다 — 값을 확인하려면 고르는 UI를 마주해야 했고, 하나를 고르면 확인 문구와 버튼 둘이 그 줄에
> 더 붙어 네 줄이 통째로 흔들렸다. 지금은 네 줄이 다 텍스트고, `변경`을 누른 줄만 컨트롤로 바뀐다.
> 확인 단계는 그대로 두 번 누르기다 (§8.1) — 예전 "바꿀까요?" 한 줄이 하던 일을 `저장`이 한다.
>
> | 결정 | 이유 |
> | --- | --- |
> | 모달 (beUI `morphing-modal`) | 행 안에서 펼치던 때는 밀리는 업무가 열 줄인 화면에서 목록이 통째로 밀려 내려갔다 |
> | 머리에 업무명을 적는다 | "모달은 어느 업무를 건드리는지 흐린다"던 v0.15의 판단을 이걸로 해소했다 — 목록이 뒤로 가려도 대상이 남는다 |
> | 고르기는 브라우저 기본 `<select>` | 모달 패널이 `clip-path`로 자기 네모를 잘라낸다. beUI `Select`의 목록은 트리거 밑에 `absolute`로 붙어서 마지막 줄에서 그대로 사라진다 (BUG-009와 같은 잘림). 기본 `<select>` 목록은 브라우저가 띄우니 무엇에도 안 잘리고 폼 값도 스스로 싣는다 |
> | 댓글은 모달로 안 올린다 | 남긴 말은 그 업무 아래에 쌓여 있어야 읽는 일과 이어진다. 행 안 접힘 그대로다 |
>
> 마감일 달력은 Portal로 나가지만 모달 레이어(`z-[100]`)보다 위로 올려야 보인다 (BUG-026).
>
> 마지막 줄은 **v2.0.0에서 뒤집혔다** — 업무가 표가 되면서 행 안에 접을 자리가 없어졌고,
> 댓글은 모달로 올라갔다.

> **본문·댓글 (v2.1.0)**: 모달 맨 아래에 업무 본문과 댓글을 얹었다
> ([task-thread.tsx](../src/components/task-thread.tsx)). 순서는 flow의 업무 상세와 같다 —
> 어느 업무인지(머리) → 지금 값(다섯 줄) → 왜 골랐는지(포커스만) → 본문 → 댓글.
>
> | 결정 | 이유 |
> | --- | --- |
> | 본문은 `flow_get_post`의 `outContent` | 실측(postId 81211887) `content`는 `contentJsonYn: "Y"`면 JSON, `htmlContent`는 태그가 붙는다. `outContent`만 그대로 낼 수 있는 평문이다. 업무 글은 본문이 비어 있는 경우가 흔해서(api-spec §6.2) 없으면 그 덩어리를 안 그린다 |
> | 댓글은 `GET /user/comments/{postId}`로 따로 | 게시글 상세의 `remarks`는 실측 14건 중 2건만 준다 (api-spec §6.3). 본문과 댓글을 `Promise.all`로 한 번에 당기고, **본문 실패는 삼킨다** — 곁가지가 죽어도 댓글은 떠야 한다 |
> | 최신 **최상위 댓글 2개**와 거기 딸린 **답글 전부**를 펼친다 (v4.2.0) | 실측 14건 중 10건이 사람 댓글이 아니라 상태·마감일 변경 기록이다. 다 펼치면 모달이 기록 목록이 된다. **답글은 수에 안 센다** — 줄 수로 자르면 부모 없는 `↳`가 첫 줄로 서서 화살표가 가리킬 대상이 화면에 없다. 목록이 `부모 → 그 답글들` 순서라 자르는 자리 하나로 둘 다 된다 (`tail`) |
> | **나를 부른 줄은 여기서도 도드라진다** (v4.2.0) | 멘션 모달과 같은 표시다 (§6.1.2) — 스레드가 길수록 내가 답할 자리를 찾기 어렵다. 판정도 같다 (`mentionsMe`). 다만 접힌 상태에서 그 줄이 위쪽이면 `댓글 다 보기`를 눌러야 보인다 |
> | 단추는 **`댓글 N개` 줄 오른쪽 끝** | 둘 다 "이 목록이 전부냐"에 대한 답이라 같은 줄에서 읽힌다. 아래 줄에 따로 두면 목록의 첫 줄처럼 보였다 (v2.2.0에 옮겼다 — 그전에는 목록 위 왼쪽이었다) |
> | 입력칸은 제일 **아래** | 위를 읽고 그 끝에 말을 붙이는 순서다 |
> | 남기면 목록을 다시 부른다 | `revalidatePath`가 실측 6.5초다 — 그동안 방금 남긴 말이 목록에 없으면 남았는지 알 수 없다 (BUG-037과 같은 부류) |
>
> 열 때 부른다. 표 열 줄에 이 덩어리를 미리 그리면 REST 열 번이다 — 모달은 한 번에 하나만 열린다.

> **답글 (v2.2.0)**: 사람 댓글 줄마다 `답글`이 붙고, 누르면 입력칸이 그 댓글에 붙는다 —
> 위에 "○○님에게 답글" 한 줄과 `그만두기`, 커서도 입력칸으로 옮긴다.
> `flow_create_comment`의 `replyToRemarkId`로 나간다.
>
> | 결정 | 이유 |
> | --- | --- |
> | 시스템 기록에는 `답글`을 안 붙인다 | 답할 상대가 없다 |
> | 남긴 뒤에는 일반 댓글로 돌아온다 | 답글 하나 달고 다음 말을 또 그 밑에 붙일 이유는 없다 |
>
> **답글이 목록에 들여쓰여 뜬다 (v4.2.0 — 앞선 결정 정정)**. `GET /user/comments/{postId}`에
> **`?replyYn=Y`를 붙이면 댓글마다 `replies[]`가 최대 10건 같이 온다** (api-spec §13.1).
> 추가 호출은 0회다. 그전에는 "답글을 읽는 경로가 없다"고 적어 두고 목록을 한 층으로 폈는데,
> 그건 쿼리를 붙이고도 **응답의 새 필드를 안 본** 결과였다 ([BUG-042](bug-report.md#bug-042)) —
> 실측 게시글 82396719는 댓글 4건 중 3건에 답글이 달려 있었고 그 대화가 통째로 빠져 있었다.
>
> | 결정 | 이유 |
> | --- | --- |
> | 답글은 **부모 바로 아래**, 한 칸 들여쓰고 말풍선 앞에 `↳` | 업무 표의 하위 업무와 같은 표시다 (§6.1.1 `IconSubTask`). 세로선은 폭이 좁아지면 흐려지는데 화살표는 폭과 무관하고, 같은 "무엇에 딸린 것"을 두 화면이 같은 모양으로 말한다. 들여쓰기는 화살표를 거들어서, 목록을 훑을 때 줄머리 위치만으로 층이 보인다 |
> | 시스템 기록 아이콘은 **되감기**(`IconHistory`) | 전에는 새 창 화살표(`↗`)를 썼는데 답글의 `↳`와 나란히 서니 둘 다 화살표라 층 표시로 읽혔다. 기록은 "지나간 일"이라 시계 쪽이 맞다 |
> | 정렬이 두 층이다 | 최상위끼리 시각순, 답글은 자기 부모 뒤에서 다시 시각순. 전부 한 줄로 섞어 시각순으로 세우면 답글이 부모에서 떨어져 나간다 — 답글은 부모보다 한참 뒤에 달리는 게 보통이다 |
> | `replyHasNext`면 나머지를 마저 받는다 | 답글이 10건을 넘는 댓글만. 실측에서 아직 참인 걸 못 봐서 보통은 호출이 0회다 (api-spec §13.3) |
> | 우리가 올린 답은 여전히 맨 아래다 | 쓰기 경로는 아직 없다 (api-spec §13.2). 남이 flow에서 단 답글만 들여쓰여 온다 |
>
> `답글` 성공 문구에서 "flow에서 볼 수 있어요" 단서는 v4.0.0에 이미 빠졌다.

> **`@` 걷기 (v2.2.0)**: 댓글 본문의 `@[이름](id)`를 **이름만** 남긴다 (`stripMentions`).
> 전에는 `@이름`으로 뒀는데, flow에서 이름을 부르는 건 알림을 보내는 동작이라 우리 화면에서는
> 누를 데도 없는 표시고, 한 댓글에 서너 명이 불려 있으면 `@`가 줄머리를 채워 본문이 안 읽혔다.
> 알림(`content`)은 서버가 이미 걷어서 준다 — 이건 댓글 API만의 문제다 (api-spec §13.1).

> **담당자 후보에 고객사도 (v3.2.0)**: 담당자 줄의 후보 목록은 참여자 조회(api-spec §5.4)
> 하나로 채웠는데, 그 API는 **우리 기관 사람만** 준다 — 프로젝트 4곳 모두 5~7명이고 전원
> `@traport.com`이다(MCP도 같은 목록, 페이징 파라미터 무반응). 같은 프로젝트 업무의 실제
> 담당자는 3~41명이고 그중 2~33명이 그 목록에 없어서, **고객사 담당자로 바꾸는 일이 아예
> 불가능했다**. 그래서 그 프로젝트 업무(`tasks/filter`)를 같이 당겨 `WORKER_ID`·`RGSR_ID`에
> 이미 이름이 있는 사람을 후보에 더한다 — `columnData[].customColumnData`가 곧 `workerId`고,
> 업무를 맡거나 낸 사람은 그 프로젝트 참여자라 쓰기의 참여자 검증에 걸리지 않는다.
> 순서는 참여자 목록 먼저, 나머지는 이름순이다. 업무는 첫 100건만 본다(`pageSize` 상한) —
> 오래된 업무에만 있는 사람은 빠지고, 그때는 기존 `참여자 목록에 없는 담당자 N명` 안내가 뜬다.

> **값을 눌러 바로 바꾼다 (v3.3.0)**: `변경` → 고르기 → `저장` 세 번을 두 번으로 줄였다.
> 상태·마감일·우선순위는 **지금 값 자체가 트리거**고, 고른 즉시 저장된다. 되돌리기가 한 번 더
> 고르는 것뿐이라 확인 단계를 뺐다 — §8.1의 "확인 **또는** 실행 취소" 중 실행 취소다.
> 담당자만 `변경`을 남긴다: 후보가 3~41명이라 값 아래 레이어에 안 들어가고, 쓰기가 덮어쓰기라
> 여럿을 켠 뒤 한 번에 보내야 한다 (별도 고르기 모달, 덮개 `z-[120]`).
>
> | 결정 | 이유 |
> | --- | --- |
> | 고르기 레이어는 라딕스 `Popover` (`z-[110]`) | 모달이 `z-[100]`이다. `onEscapeKeyDown`에서 전파를 끊는다 — 안 끊으면 레이어를 접으려고 누른 Escape가 업무 모달까지 닫는다 |
> | 트리거와 목록이 같은 `render(label)` | 전에는 목록이 맨 글자, 트리거만 배지라 "고른 것"과 "고를 것"이 다르게 생겼다. 상태는 목록도 `StatusPill`이다 |
> | 우선순위는 그림으로 넷을 가른다 | ↓ 낮음 · — 보통 · ↑ 높음 · 경보등 긴급. flow 화면이 쓰는 그림이고, 색만으로 가르지 않는다(모양 + 글자) |
> | 지금 값도 목록에 남기고 체크 | flow가 같은 값으로의 변경을 400으로 거절해서, 다시 누르면 저장하지 않고 접기만 한다 |
> | 등록일은 못 고친다 | `RGSN_DTTM`에 쓰기 엔드포인트가 없다 (api-spec §6.4에 있는 것은 `start-date`·`end-date`) |
> | **선택된 값을 지우는 것도 못 한다** | `end-date`는 `YYYYMMDD`, `priority`는 네 enum만 받는다. 값이 빈 업무는 실제로 있는데(읽기에서 `END_DT`·`PRIORITY`가 빈 채로 온다) 그 상태로 되돌리는 쓰기가 flow에 없다 |

> **본문·댓글의 주소는 새 창 링크 (v3.3.0)**: `http`·`https`로 시작하는 주소를 링크로 낸다
> ([linked-text.tsx](../src/components/linked-text.tsx)). 업무 본문·댓글 목록·멘션 알림 내용
> 세 자리가 같은 컴포넌트를 쓴다 — 같은 주소가 한쪽에서만 눌리면 안 된다. 새 창으로 여는 건
> `FlowLink`와 같은 이유다(이 자리에서 나가면 읽던 업무와 댓글이 사라진다).
> 스킴이 있는 것만 잡는다: `www.`로 시작하는 말이나 도메인처럼 보이는 파일명(`설계.v2.zip`)이
> 본문에 섞여 온다. 끝에 붙은 문장부호·닫는 괄호는 주소에서 떼고(그대로 두면 404), 한글은
> 주소에서 뺀다(`https://foo.com에서` 같은 조사).

> **도구 정정**: 최초 표는 상태 변경에 `flow_set_statuses`를 적었는데 **틀렸다.** 그 도구는
> 프로젝트의 상태 컬럼 목록 전체를 *교체*한다 (한 개만 주면 나머지 상태가 사라진다).
> 업무 하나의 상태를 바꾸는 건 `flow_update_task`다.

> **실행 취소 → 확인으로 변경**: 되돌리려면 이전 상태를 정확히 알아야 하는데, flow 커스텀
> 상태 라벨과 API enum(`request`/`progress`/`feedback`/`complete`/`hold`)이 1:1이 아니다.
> 잘못 되돌리느니 누르기 전에 묻는다. §8.1의 "확인 또는 실행 취소" 요건은 그대로 충족한다.

> **쓰기의 전제 — projectId**: 모든 쓰기 도구가 `projectId`를 요구하는데 워크리스트·스탠드업
> 응답에는 없다. `flow_list_projects`(59건)로 이름→ID 맵을 만들어 붙인다. 이름을 못 찾으면
> 쓰기 UI를 감추고 "flow에서 열어야 바꿀 수 있어요"를 대신 낸다 (추측해서 쓰지 않는다).

**쓰기 원칙**

- 실패 시 flow가 준 사유를 그대로 화면에 표시 (숨기지 않는다)
- **삭제 기능 없음.** v1에서 파괴적 액션은 제공하지 않는다
- 업무 본문 편집 없음 — flow로 링크
- 신규 업무는 항상 `요청` 상태로 생성한다. 시작도 안 한 일을 `진행`으로 넣으면 워크리스트와 스탠드업 신호가 통째로 왜곡된다

#### 6.1.5 업무 소식 — 헤더 알림 종 (§13 B1·B2)

담당 업무(`WORKER`)와 내가 올린 글(`REGISTRANT`) 알림이다. **멘션과 다른 성질이다** — 멘션은
이름이 불려서 답을 기다리지만, 소식은 "내 담당 업무가 완료로 바뀌었어요"처럼 알고만 있으면 된다.

처음엔 오늘 화면 맨 아래 카드였다. 두 가지가 걸렸다: 화면 한 자리를 늘 차지하는데 챙길 일이
아니었고, 리스크·팀 화면에서는 **아예 안 보였다.** 헤더로 올리니 세 화면 어디서나 같은 자리에
있고, 안 볼 때는 아이콘 하나로 접힌다.

| 결정                      | 이유                                                                                         |
| ------------------------- | -------------------------------------------------------------------------------------------- |
| 레이어 = 탭 + 목록 (v0.18) | 위에 탭(전체·안 읽음·읽음)과 전체 읽음 버튼, 아래에 스크롤되는 목록. 목록만 스크롤한다 — 탭과 버튼은 긴 목록에서도 손에 닿아야 한다 |
| 껍데기는 폭이 고른다 (v1.5.2) | ≥1024px는 종 아래 팝오버, <1024px는 아래에서 올라오는 바텀시트다. 판 안쪽은 **같은 것**이고 껍데기만 갈린다 (§7.3) |
| 배지는 **안 읽은 것만** 센다 | 다 읽은 줄까지 세면 배지가 늘 켜져 있어서 신호가 죽는다                                         |
| 상한 12줄 (v0.18)         | 읽은 것까지 탭으로 나눠 보게 되면서 6줄로는 "읽음" 탭이 늘 비었다. 목록이 스크롤되니 줄 수가 화면을 밀지도 않는다. 그 아래는 flow 알림함이 할 일 |
| 카드 한 장 = 네 줄 (v0.17) | 프로젝트명(굵게) · 업무명 · 내용 · 작성자. 시각은 프로젝트명 줄 오른쪽이다                      |
| 내용은 `content`가 먼저다 (v0.17) | `message`는 `"서동조님의 댓글 등록"` 같은 템플릿이라 이름은 작성자 줄에 이미 있다. 내용은 전부 `content`에 있다. 둘 다 비면 기본 문구 |
| 이름 두 개는 따로 붙인다 (v0.17) | 알림은 `projectId`·`postId`만 준다. 프로젝트명은 목록(`listProjects`), 업무명은 게시글 상세(`getPostBrief`)에서 잇고, 실패하면 그 줄만 빠진다 |
| 한 줄 = flow 문서 링크 (v0.16) | 누르면 새 탭으로 그 문서가 열리고, 같은 순간 그 알림이 읽음이 된다                        |
| 안 읽은 줄에 점             | 눌러서 읽음이 되면 점이 사라진다. 배지 숫자도 같이 줄어서 처리됐다는 게 두 군데서 읽힌다        |
| **1분 폴링** (v1.4.0)       | flow에는 푸시가 없다 — 웹훅도 구독도 없다. 종이 `/api/news`를 1분마다 당기고, 탭을 다시 보면(`visibilitychange`) 그 자리에서 한 번 더 당긴다. 숨은 탭에서는 안 부른다 |

> **딥링크 (v0.18에서 정정)**: flow가 만든 짧은 링크 `connectUrl`(`https://flow.team/l/Qmcn5`)을
> 쓴다. 게시글 상세를 업무명 때문에 이미 부르고 있어서 호출이 늘지 않는다.
>
> v0.16~0.17은 `main.act?projectId=…&postId=…`를 직접 조립했는데 **세션이 없으면 대상을 잃었다** —
> 로그인 화면으로 튕기고 나면 어느 글로 가려던 건지가 사라진다. `/l/{code}`는 `postlink`를 들고
> 로그인 화면으로 가서 로그인 뒤 그 글을 연다 ([BUG-024](bug-report.md#bug-024)). 조립한 URL은
> `connectUrl`이 없을 때의 대비로만 남긴다 (`queries.ts`의 `flowPostUrl`).
>
> 읽음 처리는 멘션과 같은 액션(`markMentionsRead` → `PATCH /user/alarms/read`)을 쓰고, §8.1의
> 확인 단계도 같은 이유로 안 둔다 — 이전 상태가 정확히 "안 읽음" 하나고 잃는 데이터가 없다.

> **폴링 (v1.4.0)**: 서버 액션이 아니라 **라우트**(`/api/news`)다 — 액션 응답에는 현재 화면 RSC가

> 채운다 (§8.1 — 공용 API 키는 넘긴 ID의 알림을 그대로 준다). 폴링 한 번의 원가는 REST 2회다:
> 알림 목록 + 프로젝트 목록. 제목·링크(`getPostBrief`)를 300초 캐시로 올려서 첫 회 이후에는
> 게시글 상세를 다시 안 부른다 — 안 올리면 분당 최대 14회였다. 조회가 실패하면 이전 목록을
> 그대로 두고 배지를 건드리지 않는다.

> **전체 읽음 (v0.18)**: 지금 불러온 소식 중 안 읽은 것만 읽음 처리한다. flow의
> `PATCH /user/alarms/read/all`은 **알림 종류를 못 가린다** (`projectId`만 받는다) — 그걸 쓰면
> 오늘 화면의 멘션 카드가 근거로 삼는 `MENTION` 알림까지 조용히 지워진다. 그래서 화면에 보이는
> `alarmId`들을 기존 액션에 그대로 넘긴다. 12건이 상한이라 호출 수도 그 안이다.

> **구조 (v0.18)**: v0.17까지 레이어는 beUI Notification Stack이었다. 접기 버튼을 걷어내자
> 남는 게 카드 목록 하나여서 스택을 물렸다 — 팝오버를 열면 Radix가 안쪽으로 포커스를 넣어
> 스택은 늘 펼친 상태였고, 겹쳐 쌓인 모습은 실제로 보이지도 않았다. 목록이 평범한 `<ul>`이 되면서
> [BUG-023](bug-report.md#bug-023)의 그리드 트랙 문제(`minmax(0,1fr)`로 막았던 것)도 같이 사라졌다.

> **바텀시트 (v1.5.2)**: 좁은 화면에서는 같은 판이 아래에서 올라온다 (beUI Bottom Sheet를
> `src/components/motion/bottom-sheet.tsx`로 들여왔다). 손잡이를 아래로 밀거나 던져서 닫고,
> 스크림을 눌러도 닫힌다. 높이는 `snapPoints=["auto"]` — 내용만큼만 선다. 목록의 상한
> (`max-h-[min(28rem,60vh)]`)이 그대로 시트의 키가 되어 375×812에서 **화면의 4분의 3**쯤에서
> 멈춘다 (실측 390×844에서 586px). 시트가 z-50이라 하단 탭(z-20) 위에 서고, 아래 여백은
> `env(safe-area-inset-bottom)`으로 홈 인디케이터를 피한다.
>
> **팝오버가 해 주던 것을 시트도 해야 한다.** Radix 팝오버는 Escape로 닫고, 열 때 안으로
> 포커스를 넣고 닫을 때 열었던 자리로 되돌린다 — beUI 원본에는 셋 다 없어서 더했다. 껍데기가
> 갈리는데 키보드 동작이 갈리면 좁은 화면에서만 기능이 나빠진다. **탭 트랩은 두지 않는다** —
> 팝오버도 비모달이라 안 잡는다. 여닫는 상태(`open`)는 종이 들고, 눌리는 단추는 폭과 무관하게
> `PopoverTrigger` 하나다: Radix가 판을 매다는 기준점이라 좁은 화면에서도 그 자리에 있어야
> 하고, 서버에서는 폭을 알 수 없어(`useNarrowScreen`이 `false`) 첫 HTML이 두 폭에서 같아야
> 번쩍임이 없다. 열려 있는 껍데기 하나만 실제로 그려진다.
>
> **업무명 (v0.17)**: 알림에는 이름이 하나도 없다 — 실측 응답 필드가 `projectId`·`postId`까지다.
> 업무명은 `GET /user/posts/{postId}`의 `title`이 유일한 출처라서 소식 줄마다 호출이 붙는다.
> 같은 업무에 댓글이 여러 개 달리는 게 흔해서 `postId`를 먼저 중복 제거하고 병렬로 부른다 —
> 상한 12줄이라 최악이 12회다. 제목 한 줄 때문에 본문·HTML·댓글 원본까지 딸려 오는 건 이 API의
> 한계다 (제목만 주는 엔드포인트가 없다). 더 무거워지면 응답 캐시가 다음 수다.

### 6.2 화면 2: 리스크 보드 (`/risk`)

59개 프로젝트를 **위험도 순 카드**로. 나열이 아니라 순위다.

위험 점수 = 밀림 건수(가중 최대) + 임박 건수 + 최장 지연 일수 + 최근 활동량

```
┌─────────────────────────────────────────────────────┐
│ ● 위험   [비즈플레이]B2603-삼성전기-출장예약 구축      │
│          밀림 11 · 임박 2 · 최장 지연 24일           │
│          ▸ 펼치면 업무 목록                          │
├─────────────────────────────────────────────────────┤
│ ● 주의   [HD한국조선해양 외 7개사] 출장관리 …         │
│          밀림 0 · 임박 1 · 최장 지연 —               │
└─────────────────────────────────────────────────────┘
```

- 기본: 위험/주의만 표시. 정상 프로젝트는 "정상 N개" 한 줄로 접음
- 부서 선택 (`/team`과 같은 탭). "내 담당만 / 전체" 필터는 부서 선택으로 대체했다
- 카드 펼침 시 업무 표(`TaskTable`) + 프로젝트에 업무 추가. 쓰기 액션은 업무명을 눌러 여는
  상세 모달 안이다 (§6.1). 카드가 이미 한 프로젝트라 프로젝트 칸을 끄고 그 자리에 **담당자**
  칸을 세운다 — 이 화면은 남의 업무가 섞여 있어서 누구 것인지가 정보다. 급함은 마감일 칸의
  D+/D- 배지가 말한다 (밀림·임박 아이콘이 하던 일이다)

> **구현 방식 변경 — 59회 조회를 1회로**: 프로젝트별 `flow_list_project_items` 병렬 조회를
> 계획했지만 실제로는 **`flow_get_team_standup(dept)` 한 번**이면 끝난다. 부서원 전원의
> 임박·밀림 업무를 통째로 주기 때문에, 그 업무들을 프로젝트 이름으로 묶으면 같은 순위표가
> 나온다. 캐시(TTL 60초)도 필요 없어졌다.
>
> **대가**: 범위가 "선택한 부서가 담당한 업무"로 좁아진다. 회사 전체 프로젝트 리스크가
> 아니다. 실무에서 필요한 건 우리 팀이 물고 있는 리스크라 이 범위를 v1 기준으로 잡는다.
>
> **점수 항목 하나 빠짐**: 스탠드업 응답에 `lastActivityAt`이 없어서 "최근 활동량" 항목은
> 계산하지 않는다. 밀림 건수 + 임박 건수 + 최장 지연 일수 세 항목으로 매긴다.
>
> **정정 (v4.0.0)**: 위 두 블록의 데이터 소스는 이제 없다. 이 화면은 팀 화면과 **같은
> `collectTasks(부서원 전원)`** 위에 서고(§6.3), 점수는 `lib/aggregate/scoreProjectRisk`가
> 매긴다. `lastActivityAt`이 없다던 제약도 없어졌다 — `tasks/filter`가 업무마다 `EDTR_DTTM`을
> 준다. 범위가 "선택한 부서" 로 좁다는 대가는 그대로다.
>
> **못 읽은 프로젝트를 화면에 적는다 (v4.1.0)**. 부서 전체를 훑는 화면이라 분당 상한에 제일
> 잘 걸리는 자리인데, 오늘·내 업무만 그 고지를 내고 여기와 팀 화면은 `collectTasks`가 준
> `failed`를 버리고 있었다 ([BUG-040](bug-report.md#bug-040)). 등급 분포와 점수는 **가져온
> 것만 센 값**이라, 빠진 프로젝트를 밝혀야 "위험 0개"가 진짜 0개인지 알 수 있다.

### 6.3 화면 3: 팀 (`/team`)

- 부서 선택 — 명단 한 번(`GET /user/search/employees`)이 사람과 부서를 같이 준다 (§6.6). 기본값 = 내 부서
- 부서 단위 집계는 `collectTasks(부서원 전원)` — 담당자 컬럼 OR 필터로 **프로젝트당 1회**다 (§5.1).
  멤버별 분류는 `lib/aggregate/classifyTasks`가 같은 응답에서 한다
- 멤버별 카드: 임박 / 밀림 / 방치 건수
- 못 읽은 프로젝트는 화면 아래에 이름으로 적는다 (`CollectNotice`, v4.1.0 — 위 §6.2와 같은 이유)
- 업무 줄은 **오늘 화면과 같은 `TaskTable`** (v0.9의 `TaskItem`을 v2.0.0에 표로 바꿨다).
  업무명을 누르면 상세 모달이 열려 상태 바꾸기·댓글이 여기서 바로 된다 — 화면을 옮기지
  않고 손을 댈 수 있어야 한다. 상태 칩은 안 건다: 여기 오는 건 한 사람의 밀림·임박 몇
  건이라 거를 게 없다
- 격자는 v2.0.0에 **3단 → 1단**(아주 넓은 화면만 2단)으로 내렸다. 표를 3분의 1 칸에 넣으면
  업무명이 열 글자에서 잘린다 (§6.1). 누가 몰려 있는지는 카드 머리의 부하 막대가 이미 말한다
- 마크다운 복사 버튼 — 주간회의 붙여넣기용

> ~~**이 화면이 MCP를 강제한다**~~ `(v4.0.0에 해소)`: `flow_get_team_standup` 한 번이 부서원별
> 임박·밀림 업무를 통째로 줬고, REST로 재현하면 부서원 × 프로젝트 = 354~472회라고 봤다
> ([§5.1.1](#511-정정-2026-07-31)). **그 산수가 틀렸다.** `filterRecords`에 같은 컬럼으로
> 레코드를 여러 개 주면 OR로 걸려서(api-spec §6.1), 부서원 8명을 한 요청에 담아 **프로젝트당
> 1회 = 59회**로 끝난다. 지금 팀 화면이 그렇게 선다 (`collectTasks(부서원 전원)`).
>
> 권한이 막지 않는다는 관찰은 그대로 유효하다 — 담당자 필터에 남의 `userId`를 넣으면 그 사람
> 업무가 실제로 나온다. 그래서 §8.1이 그 값을 **세션이나 부서 명단에서만** 채우게 막는다.

> **한계 표기**: "어제 완료한 일"은 v1에 없다. 완료 이력 집계는 별도 조회 비용이 크다. 포워드(임박/막힘) 중심임을 UI에 명시한다.

### 6.4 검색 팔레트 (`⌘K`) — 화면 위 레이어 (v0.19)

화면 셋은 **모두 "지금 챙길 일"만 보여 준다.** 워크리스트·스탠드업·알림이 근거라서, 지난달에
정리한 그 문서를 다시 찾는 길이 없다. 지금은 flow를 새 탭으로 열어서 거기서 검색한다 — 이
앱을 쓰는 동안 딱 한 가지 일만 flow로 나가야 한다.

세 번째 화면을 만들지 않는다. 검색은 목적지가 아니라 **경유지**다. `⌘K`로 어느 화면에서든
열리고, 찾으면 그 문서로 나가면서 닫힌다. 뒤에 있던 화면은 그대로 남는다.

```
┌─────────────────────────────────────────────────────┐
│ 🔍 출장관리                                    esc  │
├─────────────────────────────────────────────────────┤
│ 프로젝트                                            │
│  [프로젝트] 현대자동차 ▮출장▮ 플랫폼 …    72명       │
│  [bzp▮출장▮] 금융채널 신규 …             16명       │
│ 업무 · 글                                           │
│  ▮출장▮ 예약 화면 QA 결과                            │
│  [비즈플레이]B2603-… · 김동석 · 07/24               │
│  … ▮출장관리▮ 정산 로직 확인 부탁드립니다 …           │
└─────────────────────────────────────────────────────┘
```

| 결정 | 이유 |
| --- | --- |
| 진입은 `⌘K`(mac) / `Ctrl+K` + 헤더 아이콘 | 단축키만 두면 있는 줄 모른다. 아이콘만 두면 손이 마우스로 간다. 아이콘에 단축키를 적어 둘 다 남긴다 |
| **MCP가 아니라 REST 검색** | `flow_search`의 `title`은 **프로젝트** 제목이다 — 게시글 제목을 주는 필드가 아예 없다 (실측 2026-07-29). REST `/user/search/posts`는 `ttl`(프로젝트) · `commtTtl`(게시글) 둘 다 준다 |
| 두 묶음 = 프로젝트 5 + 글 8 | 검색 두 개를 병렬로 부른다. 프로젝트가 먼저다 — 찾는 게 "그 프로젝트"면 한 줄로 끝나고, 아니면 아래 글 목록으로 눈이 내려간다 |
| 하이라이트는 flow가 준 것을 쓴다 | 응답이 맞은 자리를 `!#!…!#!`로 감싸 온다. 우리가 다시 찾지 않는다 — 형태소를 flow가 알고 우리는 모른다 |
| 두 글자부터, 300ms 쉬면 부른다 | 한 글자는 결과가 수천이라 의미가 없고(API 최소도 1자다), 타이핑 중에 매 글자마다 두 번씩 부르면 호출이 낭비다 |
| 글 링크는 **누른 것만** 푼다 | 딥링크(`connectUrl`)는 게시글 상세를 불러야 나온다. 결과 8건을 미리 풀면 검색 한 번에 8회다. `/api/go/{postId}`가 눌린 순간 한 번 불러서 302로 보낸다 |
| 프로젝트 링크는 `main.act?projectId=` | 프로젝트에는 짧은 링크가 없다. 상세(`GET /user/projects/{id}`)의 링크성 값은 `INVT_URL`(초대 URL) 하나뿐이고, MCP도 같은 `main.act`를 준다 (실측 2회) |

> **프로젝트 링크의 한계**: 로그인 세션이 없으면 대상을 잃는다 —
> `main.act?projectId=2182810` → `signin.act?why=no-session&from=ssr-helper`(실측). 게시글은
> [BUG-024](bug-report.md#bug-024)에서 `connectUrl`로 피했지만 프로젝트에는 그 짝이 없다.
> flow를 매일 쓰는 사람이 같은 브라우저에서 누르는 게 정상 경로라 이 값으로 간다. 초대 URL은
> **쓰지 않는다** — 그건 남을 들이는 링크지 내가 들어가는 링크가 아니다.

> **읽기 전용이다**: 팔레트에서 상태를 바꾸거나 댓글을 달지 않는다. 검색 결과는 워크리스트가
> 아니라 전체 문서라서, 여기서 손을 대면 화면 셋이 쥐고 있는 "내 담당" 범위가 흐려진다.
> 손댈 일이 있으면 그 문서로 가서 한다.

> **한계 셋**: 구성원 검색(`/user/search/employees`)과 일정 검색(`/user/search/events`)은
> 넣지 않는다 — 사람은 구성원 화면(§6.6)에 전원이 있고, 일정은 오늘 화면 카드에 있다.
> 13명을 팔레트로 찾을 이유가 없다. 다음 페이지도 없다
> (`score`+`pageTargetId` 페이징은 있지만 상위 13줄이 안 맞으면 검색어를 고치는 게 빠르다).
> 화살표 키 이동도 없다 — `Tab`이 결과를 그대로 훑고 `Enter`가 연다. 목록이 길어지면 그때 붙인다.

### 6.5 화면 4: 내 업무 (`/tasks`) — 담당 업무 전량 (v1.2.0 구현)

화면 셋은 **지금 챙길 일**만 보여 준다. 그게 설계였는데, 그래서 "내가 지금 뭘 다 들고 있나"를
볼 자리가 없다. 그 차이를 실측으로 재면 이렇다 (2026-07-30, 구현 후 실측).

| 무엇                          | 건수      | 어디서 나온 값인가                                                                                                                      |
| ----------------------------- | --------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| 오늘 화면이 보여 주는 내 업무 | **16건**  | `flow_get_my_worklist`는 담당(worker) · 공개(`range_type=A`) · 진행률 100 미만만 담고, 그 안에서 또 임박 · 밀림 · 방치로 좁힌다          |
| 실제로 내가 담당인 업무       | **951건** | REST `GET /user/posts/projects/{id}/tasks/filter`에 담당자 필터를 걸어 59개 프로젝트를 전부 훑은 값. 38개 프로젝트에 있고 21개는 0건이다 |

935건이 어느 화면에도 없다. 이 화면이 그걸 담는다. 951건 중 **안 끝난 것 133건 · 끝낸 것 818건**,
마감일이 있는 건 166건뿐이다.

> 설계 때 실측(2026-07-28)은 880건이었다. 페이징 커서를 오프셋으로 계산해 프로젝트마다 첫 100건만
> 세고 있었기 때문이다 — [BUG-030](bug-report.md#bug-030). 고친 뒤가 951건이다.

**이름을 "프로젝트"로 하지 않았다.** 리스크 보드도 프로젝트 카드다 — 그쪽은 *부서가 물고 있는
위험 순위*고, 이쪽은 *내 담당 업무 전량*이다. 골격이 프로젝트여도 주인공은 업무다.

#### 데이터 경로

| 단계             | 호출                                                                                                | 실측                                                       |
| ---------------- | --------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |

| ② 프로젝트별 업무 | REST `tasks/filter` + `filterRecords=[{COLUMN_SRNO:"1", OPERATOR_TYPE:"IN", FILTER_DATA:"<내 userId>"}]` | 59회 병렬(동시 10) + 페이징. 전체 7.1초 (프로젝트 최대 3페이지) |

① 은 **MCP `flow_list_projects`가 아니다.** 설계에는 MCP로 적었는데 서버 런타임에서 그 도구가
죽어 있다 ([BUG-007](bug-report.md#bug-007)) — 리스크 보드와 같은 REST `listProjects()`를 쓴다.
제목→`projectId` 맵으로 오므로 부르는 쪽에서 뒤집는다.

**`cursor`는 페이지 번호다** (0, 1, 2…). 응답의 `lastCursor`가 다음 페이지고 끝이면 `-1`이다.
오프셋으로 계산하면 두 번째 페이지부터 조용히 빈 응답이 온다 —
[BUG-030](bug-report.md#bug-030). 프로젝트당 3페이지(300건)까지만 훑고, 더 있으면 화면 아래에
어느 프로젝트가 잘렸는지 적는다 (실측 0개).

`COLUMN_SRNO "1"`은 기본 컬럼 `WORKER_ID`다. **담당자 필터가 서버에서 걸린다** — 전량을 받아
와서 걸러 내는 게 아니라 딱 내 것만 온다. 프로젝트당 응답이 평균 23건이다.

`flow_list_projects_by_participant`는 쓰지 않는다 — 내 `userId`를 넣어도 **1개만** 준다
(api-spec §5.1의 그 엔드포인트, MCP로도 같은 값을 다시 확인했다). `flow_list_project_items`도
아니다: 담당자 · 마감일 · 업무 ID를 하나도 안 준다 (§6.2에서 쓰는 그 도구다).

#### 상태 칩만 URL을 쓰지 않는다

이 화면이 URL을 포기한 이유는 아래와 같았다. **v2.0.0에 오늘 화면도 같은 결론에 도달했다** —
표가 스스로 거르게 되면서 서버 칩(`StatusFilter`, `/?focus=진행`)을 지웠고, 이제 네 화면의
칩이 다 클라이언트 상태다. 걸러 둔 화면을 공유하는 값은 잃었지만, 그 값을 쓰는 사람을 본 적이
없고 대가는 아래 실측이다.

| 왜                     | 실측                                                                                  |
| ---------------------- | ------------------------------------------------------------------------------------- |
| 칩 한 번이 전량 재조회다 | 서버가 다시 그리면 프로젝트 59회 훑기다. 캐시가 물려 있으면 싸지만 식으면 **7초**다 |
| 3MB를 다시 받는다      | 오늘 화면은 16줄이라 공짜였다. 이쪽은 951줄이다                                        |
| URL이 38칸이 된다      | 카드마다 쿼리 키가 하나씩 붙는다 (`?s2916576=진행&s3041882=대기…`)                     |

그래서 `TaskTable`이 `useState`로 거른다. 한때 서버에서 그린 줄을 `row`로 넘기는 클라이언트
필터(`ProjectTaskFilter`)가 따로 있었는데, 표가 클라이언트 컴포넌트가 되면서 그 우회가
필요 없어졌다 — v2.0.0에 지웠다. 칩 겉모양은 `statusChipClass`·`StatusDot`으로 `StatusPill`과
한 곳에서 나눈다 (`status-filter.tsx`).

`<details>`의 `open`은 건드리지 않는다. 필터가 걸린 카드를 열어 두려고 `open`을 값으로 주면
"전체"를 눌러 필터를 풀 때 **보고 있던 카드가 접힌다** — React가 `false`로 바뀐 prop을 그대로
DOM에 쓴다. 여는 건 사람이 한다.

#### 상태가 프로젝트마다 다른 체계로 온다

같은 "완료"가 두 가지 모양으로 온다. **이걸 모르고 한쪽만 보면 업무 798건의 상태가 빈칸이 된다**
(실제로 처음 재다가 그랬다).

| 체계                     | 쓰는 곳                    | 모양                                                            |
| ------------------------ | -------------------------- | --------------------------------------------------------------- |
| `STTS` (기본, `columnId "9"`) | 표본 8개 중 **7개**        | `optionName`이 **항상 빈 문자열**이고 `customColumnData`에 숫자 코드만 온다 |
| `STATUS` (커스텀, `columnId "12"`) | 삼성전기 프로젝트 1개 | `optionName`에 라벨이 그대로 온다                               |

두 체계가 공통으로 `optionCategory`를 준다. **`"2"`가 완료다** — 완료 판정은 이 값으로 한다.
라벨은 `STTS` 코드를 다음으로 옮긴다.

| 코드  | 라벨   | 근거                                                                    |
| ----- | ------ | ----------------------------------------------------------------------- |
| `0`   | 대기   | **flow가 두 이름을 쓴다** — 시스템 기록(`SYS_CODE:"S45^^0^^2"`)은 `요청`이다. 화면은 **`대기`**로 쓴다: 사용자가 flow 업무판에서 보는 이름이 그쪽이다 (api-spec §6.1) |
| `1`   | 진행   | `optionCategory: "1"`                                                   |
| `2`   | 완료   | 위 기록의 도착점. 같은 업무의 `PROGRESS`가 100이 됐다                    |
| `3`   | 보류   | `optionCategory: "3"`                                                   |
| `4`   | 피드백 | 시스템 기록 `SYS_CODE:"S45^^4^^0"` = "'피드백' → '요청'"                 |

다섯 라벨이 [status-pill.tsx](../src/components/status-pill.tsx) `STATUS_TONE`의 키와 정확히
같다 — 색이 공짜로 붙는다. `GET /user/projects/{id}/columns/status`로는 못 푼다: `STTS`만 쓰는
프로젝트는 이 응답이 **옵션을 하나도 주지 않는다**.

> **딥링크는 조립한다.** `connectUrl`이 **880건 전부 빈 문자열**로 온다 —
> [BUG-024](bug-report.md#bug-024)에서 찾은 그 짧은 링크가 이 응답에는 없다. 대신 `projectId`와
> `postId`가 **응답에 그대로 있어서** `flowPostUrl(projectId, postId)`로 만든다. 오늘 화면은
> `projectId`를 몰라서 검색으로 해소하는데(§6.1.4 "쓰기의 전제"), 이 화면은 그 호출이 없다.
> 쓰기 액션도 같은 이유로 바로 붙는다.

> **필터 값은 반드시 로그인 세션의 `userId`여야 한다.** 공용 API 키에 **남의 ID를 넣어도 그 사람
> 업무가 나온다** — 실측이 정확히 그 경우였다 (키 소유자 ≠ 필터 대상, 전량 정상 수신).
> `loadMyTasks()`가 필터 값을 인자로 받지 않고 `getSession()`에서 직접 꺼내는 이유다.
> 필터 값(`userId`)은 **이메일**이다 — flow 짧은 아이디를 넣으면 0건이 온다.
> `mergeMentionComments`가 `receiverId`를 대조하는 것과 같은 위험이다 (§13 B6). 필터 값을
> 요청에서 받지 않고 서버에서 세션으로 채운다.

> **REST 분당 120회 상한에 이 화면 한 번이 절반이다.** 실측으로 확인했다 — 세 번째 훑기에서
> `429 RATE_LIMIT_EXCEEDED_ERROR / 요청이 너무 많습니다. (분당 최대 요청가능 횟수: 120)`.
> §12 Q3의 "rate limit 없음"은 MCP 얘기였고 REST에는 있다. **캐시**로 재진입을 막고 동시
> 호출을 10으로 묶는다. 알림 · 댓글 · 검색도 같은 예산을 쓴다.
>
> **정정 (v4.0.0)**: 오늘·팀 화면까지 같은 방식으로 옮기면서 예산이 더 빡빡해졌다. 캐시를
> **60초 → 300초**로 늘렸다 — 60초로는 오늘 화면을 보고 팀 화면을 여는 동안 캐시가 살아 있어도
> 새 59회가 붙어서, 실측으로 **59개 중 26개가 429로 떨어졌다**. 5분이면 화면을 오가는 동안
> 첫 조회 한 번으로 끝난다. 신선도는 쓰기 뒤 `revalidatePath`가 뚫는다. 그래도 떨어지는
> 프로젝트는 화면에 이름으로 적는다.

> **한계 다섯.**
> ① **하위 업무 계층은 부모가 내 담당일 때만 그린다** (v1.3.0). 처음엔 `upTaskName`이 전부 빈
> 문자열이라 평평하게 나열하고 "`mode=TREE`는 미실측"으로 닫았는데, 그게 틀렸다 — `mode`는
> 아무것도 바꾸지 않고 같은 응답의 `upTaskId`가 부모를 정확히 가리킨다
> ([BUG-034](bug-report.md#bug-034), §13 D1). 부모까지 내 목록에 있는 26/191건만 들여쓰고 나머지
> 165건은 그대로 최상위 줄이다. 없는 부모를 받으려면 건당 조회 165회고 분당 상한이 120회다.
> ② **마감일이 166/951에만 있다** — D-DAY 배지를 마감일 없을 때 안 그리도록 `TaskItem`을 고쳤다.
> ③ **우선순위는 쓰는 프로젝트에만 있다** — 표본 422건 중 44건.
> ④ **오늘 화면과 건수가 어긋난다** — 워크리스트는 진행률 100으로 완료를 가르고 우리는 상태
> 카테고리로 가른다. 둘이 어긋난 업무가 실제로 있다. 상태를 기준으로 삼는 이유는 사람이 화면에서
> 보는 값이 상태라서다.
> ⑤ **HTML이 무겁다 — 951줄이 전부 DOM에 있다** (실측 3.3MB, 첫 로드 2.8초 · 캐시 후 0.21초).
> `<details>`로 접는 방식은 접힌 내용도 마크업에 담아야 한다. 전량을 한 번에 받는다는 결정의
> 대가고, 지금 건수에서는 감당한다. 2천 줄을 넘어가면 펼칠 때 받는 쪽으로 바꾼다.

### 6.6 화면 5: 구성원 (`/members`) — 사내 주소록 ✅ v1.5.0

사람을 보는 자리는 팀 화면(§6.3) 하나뿐인데, 그건 **부서원이 업무를 얼마나 물고 있나**를 세는
화면이다. 연락처가 없다. 번호나 메일 주소가 필요하면 flow를 새 탭으로 열어야 하고, 그건 §6.4가
검색으로 막으려 했던 그 이탈이다.

전사 규모를 재면 이 화면의 크기가 정해진다 (2026-07-31 실측, `pageSize=100` 한 장).

| 무엇          | 값                                              |
| ------------- | ----------------------------------------------- |
| 구성원        | **13명** (`hasNext: false`)                     |
| 부서          | **3개** — 플랫폼개발팀 8 · 기획운영팀 3 · 경영지원팀 2 |
| 직책          | **8종** — 대표이사 · 이사 · 상무 · 부장 2 · 차장 · 과장 2 · 대리 · 사원 4 |

13명이라 이 화면에는 **페이징도, 서버 검색도, 조직도 트리도 없다.** 전부 한 번에 오고 한 화면에
들어간다.

#### 데이터 경로 — 호출 한 번

| 단계     | 호출                                        | 실측                                              |
| -------- | ------------------------------------------- | ------------------------------------------------- |
| ① 전 직원 | REST `GET /user/search/employees?pageSize=100` (api-spec §9.3) | 1회 · 13명 · `hasNext: false` |

**§3.2 `/user/employees`가 아니다.** 두 응답이 서로 다른 것을 준다.

| 필드                 | §3.2 목록 | §9.3 검색   |
| -------------------- | --------- | ----------- |
| `profileImagePath`   | **없다**  | 9/13명      |
| 휴대폰               | 있다      | 12/13명     |
| `companyPhoneNumber` | 4종       | 3/13명      |

사진이 §9.3에만 있고, 사진은 이 화면의 결정 사항이다(아래 표). 두 호출을 `userId`로 합치면
회사전화까지 오지만 **합치지 않는다** — 회사전화는 3명만 가진 공용 `02-` 번호라서 얻는 게 없다.
호출 하나로 끝낸다.

`⌘K` 검색과 같은 엔드포인트인데 §6.4가 쓰지 않는 그 도구다 — 거기서는 "사람은 다른 화면에
있다"였고, 그 다른 화면이 이제 여기다.

#### 필드 대부분이 비어 있다 — 이게 설계를 정한다

flow 스펙에 있는 필드와 **사내에 실제로 채워진 필드**가 다르다. 13명 전원을 세어 봤다.

| 필드                                                                             | 채움  | 이 화면에서 |
| -------------------------------------------------------------------------------- | ----- | ----------- |
| `fullname` · `divisionName` · `responsibility` · `email`                         | 13/13 | **쓴다**    |
| `phoneNumber`                                                                    | 12/13 | **쓴다** (없으면 줄에서 뺀다) |
| `profileImagePath`                                                               | 9/13  | **쓴다** (없으면 이니셜)      |

세울 계층이 없다. 부서는 목록을 나누는 소제목이고, 그 이상을 만들면 데이터에 없는 위아래를

> 명단은 서버 로그에 찍지 않고, 실패해도 값 없이 상태 코드만 남긴다 (§8.1과 같은 규칙 —
> 키 값을 로그에 남기지 않는 것과 같은 이유다). 응답을 디스크에 캐시하지 않는다.

> **세션 `userId` 필터가 없는 유일한 목록이다.** §6.5의 그 위험(공용 키에 남의 ID를 넣으면 남의
> 업무가 온다)이 여기엔 없다 — 이 엔드포인트는 필터 대상이 사람이 아니라 **회사**고, 전 직원
> 명단은 flow에서도 전 직원이 본다. 이 화면은 요청에서 받는 값이 하나도 없어서 조작할 표면 자체가
> 없다.
>
> 다만 v1.5.1에 `searchEmployees`가 **검색어 인자 하나**를 갖게 됐다 (계정 블록이 자기 사진 한
> 장을 받는 데 쓴다 — §7.3). 그 값은 **세션에서만** 채운다. 요청에서 받은 문자열을 그대로 흘리면
> 남의 이름으로 전 직원 명단을 훑는 손잡이가 된다 — 공용 API 키라 검색은 통한다. 인자 이름을
> `sessionSearchWord`로 둔 게 그 규칙을 호출부에서 읽게 하는 장치다 (§8.1과 같은 규칙).

> **한계 셋.** ① **100명 상한** — `pageSize=100` 한 장만 받는다. 13명이라 남지만, 넘으면
> `listEmployeeIds`처럼 커서 루프를 붙인다 (그때는 부서 탭도 서버로 옮겨야 한다).
> ② **부서 이동·퇴사가 반영되는 시점을 우리가 모른다** — flow가 주는 대로 그린다. 재직 여부를
> 가릴 `status`가 값 하나뿐이라 **퇴사자가 섞여 있어도 구별하지 못한다**.
> ③ **이메일 ≠ `userId`인 사람이 1명 있다.** 주소록은 이메일을 보여 주지만 멘션·담당자 필터가
> 쓰는 키는 `userId`다 (§6.5). 이 화면에서 복사한 주소를 그런 자리에 넣으면 0건이 온다 — 그래서
> 이 화면은 `userId`를 **화면에 내지 않는다.** 메일 보내는 주소와 시스템 키를 한자리에 나란히
> 두면 헷갈릴 게 뻔하다

## 7. 디자인 시스템

**스타일**: Data-Dense Dashboard — 정보 밀도 우선, 그리드 레이아웃.
**안티패턴**: 장식적 디자인, 필터 없는 목록.

**여백은 세 급이다** (v1.7.0). 원래 "여백 최소"였는데 본문 32 · 카드 안쪽 16 · 구획 사이 24가
사실상 한 급이라 화면 전체가 같은 밀도로 촘촘했다 — "답답하다"의 정체였다. 밀도를 낮춘 게
아니라 **급을 벌린 것**이다: 카드 안쪽 `20`(작은 카드 `16`) → 카드 사이 `32` → 구획 사이 `40`.
셋이 벌어져야 "한 덩어리 / 이웃 / 다른 이야기"가 눈으로 갈린다. 카드 안쪽은
`Card`의 `--card-spacing` 한 곳에서만 정한다 (`src/components/ui/card.tsx`).

폭 규칙은 그대로다 (아래 fluid). 답답함은 밀도 문제라 폭을 건드릴 자리가 아니다.

### 7.1 컬러 토큰

`-foreground` 파생값은 같은 계열 배경 위 **텍스트용**이다. 원본 토큰은 아이콘·인디케이터에만 쓴다.
상태색은 `-bg` 배지 면(`danger-bg` 등)까지 세 벌이라 밝기별로 같이 뒤집힌다.

**회색은 무채색이다.** 배경·카드·경계선에 색기를 섞으면 흰 카드와 나란히 놓일 때 그 기울기가
얼룩처럼 보인다. 밝게는 흰 표면 + 무채색 회색 + 파랑 액센트, 어둡게는 남색 계열 3단 표면이다.

**밝게의 강조색은 v1.7.0에 검정(`#171717`)에서 파랑으로 바꿨다.** 검정은 대비는 좋았지만 화면에
유채색이 나올 자리가 아예 없어서 — 활성 메뉴도 링크도 아이콘도 전부 회색 아니면 검정 — 다섯
화면이 흑백 표로 읽혔다. 어둡게가 이미 파랑이라 두 모드가 서로 다른 브랜드로 보이기도 했다.
값은 `#1D4ED8`(흰 바탕 6.7:1)이다. 어둡게의 `#2F6FEB`을 그대로 올리면 4.57:1이라 작은 글자에서
아슬아슬하고, 무엇보다 `#2563EB`(흔한 파랑)는 `info`와 **같은 값**이 돼서 브랜드 파랑과 상태
파랑이 구분되지 않는다. 한 단 짙게 잡아 "브랜드 파랑이 상태 파랑보다 무겁다"는 관계를 만든다.

**상태색은 배지 밖에서도 쓴다** (v1.7.0). 요약 카드가 뜻에 맞는 색 면(`from-X/10 to-X/0`
그러데이션)과 아이콘 칩을 갖고, 카드 제목 표지가 같은 톤을 이어받는다 — 지도 하나
(`KPI_TONE`, `src/components/kpi.tsx`)를 요약과 제목이 같이 읽어서 두 자리가 절대 안 어긋난다.
두 가지 제약이 붙는다:

| 제약 | 이유 |
| ---- | ---- |
| `neutral` 톤에는 색 면이 없다 | 넉 장을 다 물들이면 물든 게 기본이 돼서 다시 아무 신호도 아니다. 물들지 않은 칸이 있어야 물든 칸이 읽힌다 |
| 면은 배경색이 아니라 **그러데이션**이다 | `bg-X/10`은 `background-color`라 `bg-card`를 덮어써서 어둡게의 3단 표면이 무너진다. `bg-linear-to-b`는 `background-image`라 카드 색 위에 얹힌다 (tailwind-merge도 다른 묶음으로 본다) |
| 장식으로는 안 쓴다 | 색이 붙은 자리는 전부 뜻이 있다 — 상태·우선순위·위험도·"지금 여기"·"누를 수 있다". 부서 이름처럼 뜻 없는 자리는 회색으로 둔다 |

**구현은 CSS `light-dark()` 한 줄이다.** 토큰 하나에 선언 하나:

```css
:root {
  color-scheme: light dark; /* 클래스가 없으면 기기 설정 */
  --primary: light-dark(#1d4ed8, #2f6feb);
}
.light {
  color-scheme: light;
} /* 값은 위에서 이미 골랐다 */
.dark {
  color-scheme: dark;
}
```

`:root`와 `.dark`에 팔레트를 두 벌 적는 흔한 방식을 안 썼다 — 색 하나를 고칠 때 두 곳을
고쳐야 하고, 한 곳을 빠뜨리면 한쪽 밝기만 틀린다. `light-dark()`는 값이 한 줄에 나란히 있어서
빠뜨릴 자리가 없다. 클래스는 `color-scheme`만 뒤집는다.

**고른 값은 쿠키에 둔다** (`localStorage`가 아니라). 서버가 첫 HTML을 그릴 때 쿠키는 요청에
실려 오니 `<html class="dark">`를 처음부터 맞게 박는다 — 화면이 한 번 번쩍이지 않고, 이걸 막는
blocking script도 필요 없다. `system`은 클래스를 아예 안 붙여서 위 `color-scheme: light dark`가
기기를 따라간다 (기기 설정 변화를 지켜보는 코드가 없다).

| 한계                                     | 이유                                                                        |
| ---------------------------------------- | --------------------------------------------------------------------------- |
| 모바일 주소창 색은 **기기 설정**을 따른다 | `themeColor` meta는 media 쿼리만 받는다. 기기 어둡게 + 앱 밝게면 주소창만 어둡다 |
| PWA 설치 스플래시는 늘 어둡다             | 매니페스트 `theme_color`가 한 칸뿐이다 — 원래 얼굴 쪽으로 뒀다               |

**업무 상태 배지 색은 flow 화면을 그대로 따른다** (요청=파랑, 진행=초록, 피드백=주황, 완료=보라, 보류=회색). Cockpit에서 다른 색을 쓰면 같은 상태를 두 번 배워야 한다. `info`·`done` 두 토큰은 이걸 맞추려고 추가했다. flow는 프로젝트마다 상태 라벨을 바꿀 수 있어서(커스텀 상태) 응답이 문자열로 온다 — 아는 라벨만 칠하고 모르면 회색으로 둔다.

상태는 **색만으로 전달하지 않는다.** 아이콘 + 텍스트 라벨을 항상 동반 (WCAG `color-not-only`). 마감은 `D-2` / `D+24`처럼 부호를 붙여 색 없이도 읽히게 한다.

### 7.2 타이포그래피

> 디자인 추천 엔진은 Fira Sans를 제시했으나 **한글 글리프가 없어 폴백이 발생한다.** UI가 전부 한국어이므로 본문은 SUIT으로 대체한다.

| 역할                           | 폰트                    |
| ------------------------------ | ----------------------- |
| 본문 / 제목 / 숫자 · ID · 날짜 | **SUIT** (100~900, 9단) |

**서체는 SUIT 하나다.** 숫자도 같은 서체를 쓴다. 원래 숫자 컬럼만 별도 mono(Fira Code)였는데,
목적(자릿수 흔들림 방지)을 SUIT으로 그대로 달성할 수 있는 걸 실측으로 확인해서 걷어냈다 —
화면에 서체가 둘 섞여 보이는 값을 낼 이유가 없었다.

지연 일수·건수 등 숫자 컬럼은 `.tabular` 유틸을 붙인다:

```css
.tabular {
  font-variant-numeric: tabular-nums;
  font-kerning: none;
}
```

`font-kerning: none`이 핵심이다. SUIT의 숫자 자폭은 `tabular-nums`에서 전부 같은데
(100px 기준 61.8), `1`+`1` 커닝 페어가 붙으면서 `"11"`만 좁아진다. 커닝을 끄면
`11.11 11:11`과 `07.27 15:16`이 정확히 같은 폭(572.1px)이 된다.

타입 스케일: 12 / 14 / 16 / 18 / 24 / 32. 본문 16px, line-height 1.5.

### 7.3 레이아웃

- 브레이크포인트: 375 / 768 / 1024 / 1440
- ≥1024px: **좌측 레일 + 본문 헤더**
  - 레일(펼침 240px / 접힘 68px)이 화면을 위에서 아래까지 쓴다. 머리에 브랜드, 가운데
    검색(⌘K)과 메뉴(오늘 / 리스크 / 팀), 발에 계정이다. 헤더는 본문 칸 위에만 있고
    접기 단추 · 세로선 · 지금 있는 화면 이름 · (오른쪽) 밝기(§7.1) · 알림 종(§6.1.5)을 든다.
  - **접힘은 쿠키에 남긴다** (`sidebar=0|1`). 서버가 첫 HTML을 접힌 폭으로 그려야
    240 → 68px로 접히는 번쩍임이 없다 — 밝기와 같은 방식이다. `⌘B`로도 여닫고 기본은 펼침.
  - **계정은 레일 발이다.** 이름·부서·로그인한 이메일 세 값을 내고, 마우스를 올리면(또는
    Enter) 오늘 일정·로그아웃이 든 팝오버가 옆으로 열린다. 호버로 열지만 `HoverCard`가 아니라
    `Popover`다 — HoverCard 안은 키보드로 짚을 수 없어서 그 안의 로그아웃이 마우스 없는
    사람에게는 없는 기능이 된다. 계정 칸 높이는 페이지 푸터와 같은 **81px**이라 두
    `border-t`가 한 줄로 이어진다.
  - **28px 원판은 flow 프로필 사진이다** (v1.5.1). 그전엔 `👋🏻`이었다 — 이름이 바로 옆에
    적혀 있어서 이니셜을 한 번 더 낼 이유가 없었기 때문인데, **접으면 이 원판만 남아서**
    그때는 얼굴이 손보다 알아보기 쉽다. 사진이 없는 사람(13명 중 4명)은 손을 그대로 쓴다.
    세션에 사진이 없어서 §6.6과 같은 REST §9.3에 한 번 더 묻는다 — 검색어는 **세션 이름**이고
    받은 줄에서 **이메일로** 고른다(검색어에 이메일을 넣으면 0명이고, 이름으로는 동명이인이
    같이 온다 — 실측). 실패하면 빈 문자열이라 셸이 넘어지지 않는다. 사진 한 장 때문에 다섯
    화면이 같이 죽을 이유가 없다.
  - **팝오버에 상태 메시지 한 줄** (v1.5.1). 같은 응답에 `slogan`이 실려 온다. 위 세 줄은

  - **팝오버에 "나의 일정"** (v1.6.0, v1.8.0에 이레로). 누르면 오른쪽에서 서랍이 들어온다

    일이 잦다. 건수는 서랍을 열지 않아도 보이게 **단추에 함께 적는다** (0건이면 안 적는다).

      첫날로 세는 롤링 이레다 — 달력으로 자르면 금요일에 열었을 때 이틀치만 남아서 답이

      줄에만 파란 `오늘 ·`이 앞에 붙는다. 시각만 늘어놓으면 `15:16`이 어느 날 세시인지
      알 수 없다. 팀 화면의 부서원 일정(`memberEvents`)은 하루 그대로다 — 거기는 "이 사람이
      지금 자리에 있나"라 이레가 필요 없고, 사람 수만큼 왕복이 늘어난다.
    - **줄에 색·참석·반복·프로젝트 링크** (v1.9.0). 시각 옆에 달력 색 막대(`eventColor`가
      비면 `calendarColor`로 떨어진다. `hexColor`가 6자리 hex만 통과시킨다 — 응답 값을
      `style`에 그대로 꽂는 자리다), 이름 뒤에 참석 표시(`attendanceStatus`)와 반복
      표시(`repeatSrno`), 프로젝트 일정이면 아래에 `FlowLink`(`colaboSrno` →
      `flowProjectUrl`)다. 넷 다 §8.2 목록 응답에 이미 있어서 호출이 안 늘어난다.
      달력 이름은 **달력이 여럿일 때만** 적는다 — 하나뿐이면 그게 곧 내 이름이라 줄마다 같은
      말이 반복되고, 여럿이면 반대로 그 이름이 색의 범례가 된다 (색만으로 뜻을 나르지 않는다).
    - **참석 표시는 `"ATTENDING"`만 그린다.** 값 목록이 명세 어디에도 없다 — §8.2·§8.5·§9가
      다 필드 이름만 적어 뒀고, MCP 쓰기 도구도 참석 응답을 다루지 않는다. 실측으로 본 건
      `"ATTENDING"`과 `""` 둘뿐이라 나머지는 아무것도 안 그린다. 모르는 값을 "불참"으로
      오독하느니 안 그리는 편이 낫다 — 대신 불참으로 응답한 일정이 무표시 일정과 같아 보인다.
      상세(§8.5)의 최상위 같은 이름 필드는 비어 있고 내 응답은 `attendances[]` 안에만 있어서
      목록과 어긋난다. 목록 응답의 값만 믿는다.
    - **뺀 것**: 장소·참석자 명단·회의 링크·반복 주기는 일정마다 상세(§8.5)를 한 번씩 더
      불러야 나와서 안 넣었다. 펼쳐 보는 손짓을 먼저 두고 그때 부르는 게 순서다.
    - 서랍이 **오른쪽**인 것은 여는 자리가 왼쪽 레일 발이라서다. 왼쪽에서 열면 방금 누른
      그 레일을 덮는다. 팝오버 밖에 두는 것도 같은 이유다 — 팝오버는 열리는 순간 닫힌다.
    - 데이터는 셸이 받는다 (`loadWeekEvents`). 부르는 자리가 레이아웃 하나라 화면이 무엇이든
      요청당 REST 왕복은 **하나다**. 오늘 날짜(`today`)도 같은 함수가 창의 시작과 같은
      시각에서 뽑아 내려준다 — 판에서 `Date.now()`를 읽으면 수화가 깨진다.
    - 서랍을 닫을 때 **초점을 계정 줄로 직접 돌려준다.** 서랍 자체의 복귀는 이미 사라진
      팝오버 단추를 겨눠서, 없으면 Escape 뒤 초점이 `body`에 남는다 (실측).
  - 한때 **상단 바 2행**이었다 (v0.9.3~v0.23.0). 목록 위주 화면이라 좌측 240px을 늘
    내주는 게 아까워서 올렸던 것인데, 헤더 오른쪽에 컨트롤 여섯 덩어리가 늘어서면서
    `⋯` 원판으로 묶었다 풀었다를 반복했다 (v0.22.0 → v0.23.0). 레일에는 그 여섯을 머리·
    가운데·발로 나눠 담을 자리가 있고, 접으면 본문 폭도 68px만 내준다.
  - 헤더는 `sticky` + 반투명(`bg-card/55`) + `backdrop-blur-2xl backdrop-saturate-200`.
    스크롤 시 본문이 비쳐서 고정된 바라는 게 읽힌다. 배경이 근검정이라 통과할 색이
    적다 — alpha 70% + blur만으로는 효과가 눈에 안 띄어서 alpha를 열고 채도를 올렸다.
- <1024px: 상단 앱바 + 하단 탭 5개 (엄지가 닿는 곳). 레일은 없다 — 앱바가 검색·밝기·일정·
  소식·로그아웃을 들고, 이니셜 원판은 두지 않는다. 로그인은 한 계정뿐이라 누구인지 확인할
  일이 없고, 원판까지 서면 종과 로그아웃 사이가 좁다.
  - **이 선에서 레이어도 갈린다** (v1.5.2). 앱바에 매달리는 판(§6.1.5의 소식)은 여기서
    바텀시트가 된다 — 폭을 거의 다 쓰는 판이 손이 가장 안 닿는 오른쪽 위 구석에 붙어 열리고,
    좁은 화면에서 닫는 유일한 길인 "빈 곳 누르기"는 누를 빈 곳이 없다. 판정은
    `useNarrowScreen()`이 하고 폭은 셸의 `lg:hidden`과 **같은 1024px 하나**를 읽는다.
    두 군데에 적어 두면 어느 날 한쪽만 움직인다.
  - **나의 일정도 여기서는 앱바 + 바텀시트다** (v1.6.0). 계정 팝오버가 넓은 화면 전용이라
    여는 자리가 없어서 앱바가 대신 든다 — 검색·로그아웃과 같은 짝이다. 서랍이 아닌 것은
    위 문단과 같은 이유고(320px 판이 390px 화면에서 스크림을 한 뼘만 남긴다), 판 안쪽은
    서랍과 **같은 것을 쓴다** (`ScheduleList`). 여기는 껍데기를 고르는 게 아니라 좁은 화면
    전용 단추 하나라 `useNarrowScreen()` 없이 `lg:hidden`으로 가른다.
    건수 배지는 안 단다 — 옆의 종이 쓰는 표시라 같은 모양이면 안 읽은 소식으로 읽힌다.
    대신 읽어 주는 이름(`sr-only`)과 시트 설명 줄에 적는다.
- **업무명·프로젝트명은 한 줄에서 자른다** (`truncate`). 길이에 따라 줄이 2단·3단으로
  들쭉날쭉하면 목록을 훑는 눈이 자리를 잃는다. 전문은 펼침(멘션)이나 `flow에서 보기`로 본다.
  같은 이유로 멘션 줄의 메타(상태·프로젝트·사람·시각)는 접지 않고 프로젝트명만 줄어든다.
- **폭은 fluid다.** 최대폭을 두지 않고 화면을 꽉 쓴다 — 원래 `max-w-7xl`(1280px) 중앙
  정렬이었는데, 목록·카드 위주라 넓어지는 만큼 한 행에 담기는 정보가 늘어난다. 대신 좌우
  여백을 `px-4 → sm:px-6 → lg:px-10`로 벌린다. 헤더와 본문이 같은 규칙을 써서 화면 이름과
  본문 `h1`이 한 줄에 선다 (넓은 화면 좌우 40px, v1.7.0에 32→40).
- 4/8px 스페이싱 스케일
- 가로 스크롤 금지. 표는 자체 `overflow-x: auto` 컨테이너 안에서만
- 한글 조판: `word-break: keep-all` + `overflow-wrap: break-word`(영문 코드 대비),
  제목에 `text-wrap: balance`

### 7.4 인터랙션

- 트랜지션 150~300ms, 진입 `ease-out` / 이탈 `ease-in`
- `transform` / `opacity`만 애니메이션 (레이아웃 리플로 금지)
- 행 hover 하이라이트, 클릭 요소에 `cursor-pointer`
- 로딩 300ms 초과 시 스켈레톤 (스피너 아님). **골격은 화면마다 다르다** — 아래 §7.4.1
- 본문이 터지면 **셸은 남는다.** `(app)/error.tsx`가 본문 자리만 오류 카드로 바꾼다 — 없으면
  flow 호출 한 번이 실패할 때 헤더·탭바·푸터까지 같이 사라진다. 원인이 대개 토큰 만료라
  `다시 시도`(서버에 새로 묻기)와 `다시 로그인` 두 길을 함께 둔다.
- 진입 모션은 **CSS 캐스케이드**. `.rise` / `.bar-grow` + `animation-delay: calc(var(--i) * 45ms)`로
  카드가 순서대로 올라온다. `animation-fill-mode: backwards`가 있어야 지연 중에 최종 상태가
  번쩍이지 않는다. IntersectionObserver를 쓰지 않아 서버 컴포넌트에 클래스만 붙이면 된다.
- `prefers-reduced-motion` 준수 — duration만이 아니라 **`animation-delay`도 0으로** 지운다.
  안 그러면 `backwards`로 대기하던 요소가 지연 시간 동안 안 보인다.
- 아이콘은 **Lucide SVG**. 이모지 금지

#### 7.4.1 골격 (스켈레톤)

REST 왕복이 초 단위다 (오늘 화면 한 번이 81회, api-spec §12). 골격이 없으면 메뉴를 눌러도 **이전 화면이 그대로 남아** 눌렸는지조차
안 보인다. 셸(레일·헤더·탭바)은 즉시 서고 본문 자리만 골격으로 채운다 — `loading.tsx`가 그 일을 한다.

| 규칙 | 왜 |
| --- | --- |
| **틀은 진짜, 글자만 회색 막대** | 실제 화면과 같은 `Card`·격자 클래스를 그대로 쓰고 글자 자리만 막대로 둔다. 네 화면이 제목 + 카드 3장짜리 골격 하나를 같이 쓸 때는 단 수와 칸 폭이 달라서 내용이 도착할 때마다 배치가 한 번 튀었다 — 골격이 막으려던 그 튐이다 |
| **화면마다 자기 골격** | `(today)`·`risk`·`team`·`tasks` 각자 `loading.tsx`를 갖는다. 부분은 `components/skeletons.tsx`에서 나눠 쓴다 (`HeadSkeleton`·`KpiRowSkeleton`·`PanelSkeleton`·`TaskRowsSkeleton`·`SummaryCardsSkeleton`·`CommentRowsSkeleton`·`TabBarSkeleton`) |
| 오늘 화면은 **`(today)` 무리 안** | `(app)/loading.tsx`에 두면 자식 경로 셋의 **부모** 경계가 되어 오늘 골격이 먼저 깜빡인다 ([BUG-032](bug-report.md#bug-032)). 무리 이름은 URL에 안 나온다 |
| 골격에 `rise`를 안 붙인다 | 진짜 카드가 `rise`로 올라온다. 골격도 올라오면 한 화면에서 같은 모션이 두 번 돈다 |
| 탭 줄은 알약이 아니라 **막대 하나** | 탭 수를 서버가 답하기 전에는 모른다 (부서 수 · 안 빈 무리 수). 세 개를 그려 놓고 두 개가 오면 그게 튐이다 |
| 색은 `bg-foreground/8` | `bg-muted`는 밝은 화면에서 배경과 같은 색이라 안 보였다 ([BUG-031](bug-report.md#bug-031)) |
| 화면 안 기다림도 같은 규칙 | 스레드 댓글(`CommentRowsSkeleton` 3줄) · 참여자 알약 5개 · 검색 결과 3줄. 전에는 `찾고 있어요` 같은 글자 한 줄이었는데, 결과가 오면 레이어 높이가 열 배로 뛰거나 저장 버튼이 손 아래에서 밀렸다 |
| 이미 결과가 떠 있으면 골격을 세우지 않는다 | 검색을 다시 할 때 있던 결과를 회색 줄로 바꾸는 건 뒤로 가는 것이다. 입력 칸의 도는 아이콘이 활동을 알린다 |
| 골격은 **자기 줄을 차지한다** | 막대 폭이 비율(`w-full`)이라 부모가 폭을 정해 줘야 뜻이 있다. 버튼 줄 안의 `flex` 항목으로 들어가면 폭이 버튼 글자만큼 줄어 130px 막대가 된다 — 멘션 카드의 `ThreadView`가 그랬다 ([BUG-033](bug-report.md#bug-033)). `basis-full`로 한 줄을 준다 |

골격을 안 세우는 자리도 있다. 업무 줄의 **마지막 댓글**은 자리를 미리 비우지 않는다 — 실측
대부분의 업무에 댓글이 없어서, 막대를 세워 두면 없는 줄마다 접히는 움직임이 한 번씩 생긴다.

## 8. 비기능 요구사항

### 8.1 보안

Vercel 배포 = 공개 인터넷이다. 네트워크 경계가 없으므로 인증이 유일한 방어선이다.

| 항목      | 요구사항                                                              |
| --------- | --------------------------------------------------------------------- |
| 토큰      | 액세스/리프레시 토큰 브라우저 노출 금지. 서버 세션 전용               |
| 개인 API 키 | 토큰과 같은 취급. AES-256-GCM 봉인 `httpOnly` 쿠키 전용 (`fc_key`). 키 값을 화면 메시지·로그에 남기지 않음 |
| 권한      | flow OAuth 위임 권한을 그대로 사용. 자체 권한 로직 금지               |
| 회사 검증 | 로그인 직후 소속 회사가 트래포트인지 확인. 아니면 세션 파기           |
| 로그      | 업무 제목·본문을 애플리케이션 로그에 남기지 않음 (고객사명 다수 포함) |
| 인덱싱    | `robots: noindex, nofollow`                                           |
| 쓰기      | 모든 쓰기 액션은 실행 취소 또는 확인 단계를 가진다                    |
| 시크릿    | `client_secret` 등은 Vercel 환경변수. 저장소에 커밋 금지              |

### 8.2 접근성 (WCAG 2.1 AA)

- 본문 대비 4.5:1 이상, 큰 텍스트 3:1 이상
- 전체 키보드 조작 가능. 포커스 링 제거 금지
- 아이콘 전용 버튼에 `aria-label`
- 상태 변경 결과는 `aria-live="polite"`로 안내
- 폼 에러는 필드 바로 아래 + 원인과 해결 방법을 함께 명시

### 8.3 성능

| 지표                       | 목표                                       |
| -------------------------- | ------------------------------------------ |
| 오늘 화면 첫 유의미 콘텐츠 | 1.5초 이내 (캐시 히트 시)                  |
| 리스크 보드 (59개 롤업)    | 캐시 3초 / 콜드 10초 이내, 그동안 스켈레톤 |
| CLS                        | < 0.1 (비동기 영역 공간 예약)              |
| 리스트 50행 초과           | 가상 스크롤                                |

블록별로 독립 스트리밍한다. 리스크 보드 롤업이 느리다고 오늘 화면 전체가 막히면 안 된다.

## 13. REST 확장 후보 (v0.5 신설)

§5.1.1의 하이브리드 확정에 따라, **MCP에 길이 없는 기능**을 REST에서 골라 등급을 매긴다. 전부 2026-07-28 인증된 실제 호출로 확인했다 — 근거 없는 후보는 넣지 않았다.

> **v4.0.0 기준으로 읽는 법**: 고르는 기준이었던 "MCP에 길이 없는가"는 이제 의미가 없다 ([§5.1.2](#512-전면-정정-2026-08-04-v400--mcp를-걷었다)). 남는 기준은 **지금 화면에 있는 구멍을 막는가** 하나이고, 그건 아래 등급 기준과 같다. 표는 그대로 유효하다.

등급 기준은 하나다: **지금 화면에 있는 구멍을 막는가.** 새 화면을 여는 것보다 반쪽으로 서 있는 곳을 채우는 게 먼저다.

> **상태 (v0.15.0)**: **Tier A 5종 · Tier B 6종 전부 구현됐다.** Tier C는 착수하지 않는다 — 아래 표를 남겨 두는 이유는 §13 끝에 적었다. 구현 중에 바뀐 판단은 표 아래 인용에 이어 적었다.
>
> **v0.16.0**: B1·B2(업무 소식)에 딥링크와 한 줄 읽음 처리를 붙였다 (§6.1.5). A2의 `PATCH /user/alarms/read`를 그대로 재사용해서 새 API는 없다.
>
> **v0.17.0**: 소식 카드를 네 줄로 세우면서 업무명을 붙였다 — `GET /user/posts/{postId}`(§6.3)를 처음 호출한다. 알림에 이름이 없다는 §13의 전제는 그대로고, 없는 걸 지어내지 않으려면 호출을 하나 더 붙이는 수밖에 없었다.
>
> **v0.18.0**: 소식 레이어를 탭(전체·안 읽음·읽음) + 전체 읽음 버튼으로 다시 짰다 (§6.1.5). 딥링크는 조립을 그만두고 같은 게시글 상세가 주는 `connectUrl`로 바꿨다 — 조립한 URL은 로그인 화면에서 대상을 잃었다 ([BUG-024](bug-report.md#bug-024)). A2의 `/read/all`은 여기서도 안 쓴다: 알림 종류를 못 가려서 멘션까지 지운다.
>
> **v0.19.0**: Tier 목록에 없던 블록을 하나 더 열었다 — **검색**(`GET /user/search/posts` · `/projects`, api-spec §9). §6.4의 검색 팔레트다. 이 절이 REST를 후보로 세울 때 검색은 "참고용"으로 미뤄 뒀는데, 실측하니 MCP `flow_search`가 게시글 제목을 아예 안 준다 — 이 화면은 REST만 만들 수 있다.

두 관측이 같은 방향을 가리킨다 — 참여가 아니라 소유/관리 권한을 보는 듯하다. §6.3 팀 화면이나 주간
보고를 chain 계열에 얹을 수 없다 ([BUG-011](bug-report.md#bug-011) 재측정으로 기록).

#### D3 — 실재하지만 수요 근거가 없다 (Tier C 대우)

| 후보                     | 경로                                                     | 왜 미루나                                                                                          |
| ------------------------ | -------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 하위 업무 만들기         | `POST .../tasks/{taskId}/subtasks` (`progress` 포함)      | D1로 계층을 **보여준 다음에** 나올 요구다. 지금은 만든 것이 앉을 자리가 없다                        |
| 체크리스트               | `flow_create_todo` (1~50건)                              | 업무 아래 체크리스트를 우리 화면이 아예 안 읽는다. 읽기가 먼저다                                    |
| 일정 만들기              | `flow_create_schedule` · 캘린더 쓰기 4종 (api-spec §8.6)  | 일정은 읽기만 쓴다(§6.1 오늘 카드). 만들기 요청이 없었다                                            |
| 댓글 수정                | `flow_update_comment`                                    | 오타를 고칠 길이 없는 건 사실이다. 다만 `projectId`+`postId`+`remarkId`가 다 필요하고 첨부는 병합이 아니라 교체다 |
| 만든 업무 "열어보기"     | `POST .../tasks` 응답의 `tinyUrl`                        | 지금은 MCP `flow_create_task`로 만들고 응답을 버린다([actions.ts:122](../src/app/(app)/actions.ts#L122)). 링크를 얻으려면 쓰기를 REST로 옮겨야 하고 그러면 상태 enum 처리를 우리가 떠안는다(api-spec §6.4). 링크 하나 값이 아니다 |

#### D4 — 찾다가 없어진 것

- **즐겨찾기·최근수정 정렬**: `flow_search_project`는 `favoriteStatus`·`updatedAt`을 주는데, 목록에
  쓰는 `GET /user/projects`는 **`projectId`·`title`·`projectUrl` 3개만** 준다(실측). §6.5의 프로젝트
  정렬을 즐겨찾기로 바꾸려면 전량 목록을 검색 도구로 대체해야 한다 — 그건 조회 경로가 아니다. 안 한다.
- **알림 답글 구분**: 이미 쓰고 있다 — `replyId !== "-1"`
  ([rest.ts:958](../src/lib/flow/rest.ts#L958)). 후보에서 빠진다.

> **이번 재점검이 남긴 것은 D1 하나다.** 나머지는 "권한이 막는다"거나 "근거가 없다"로 닫혔다.
> D1은 새 호출이 0회고 잘못된 한계 표기(§6.5 ①)를 지운다 — 이 절의 기준으로 가장 싼 항목이다.

## 부록 A. 사용 REST 엔드포인트 `(v4.0.0 — MCP 목록을 대체한다)`

Endpoint: `https://api.flow.team` · 인증: `x-flow-api-key: <개인 API 키>` · 상한 **분당 120회**

전부 [rest.ts](../src/lib/flow/rest.ts) 한 파일에 가둔다. 화면 코드는 HTTP를 모른다.
필드 의미와 응답 예시는 [api-spec.md](api-spec.md), 호출 순서는 그 문서 §12다.

**읽기**

| 함수 | 엔드포인트 | 용도 |
| --- | --- | --- |
| `getMe` | `GET /user/employees/me` | 신원 · `@traport.com` 도메인 검증 (§5.2.1). 로그인 때 1회 |
| `listProjects` | `GET /user/projects` | 프로젝트 전량 59개. 커서 페이징 |
| `listWorkerTasks` | `GET .../tasks/filter` (담당자 필터) | **네 화면 전부의 원천.** 여러 담당자를 OR로 받는다. 300초 캐시 |
| `listStaleTasks` | 같은 엔드포인트 | 검색 팔레트가 쓰는 무필터 조회 |
| `listStatusOptions` | `GET .../columns/status` | `optionSrno` → 상태명·완료 여부 |
| `getTaskFields` | `GET .../tasks/filter` 단건 | 상세 모달의 지금 값(우선순위·담당자) |
| `getPostBrief` | `GET /user/posts/{postId}` | 업무명 · 본문 · 짧은 링크 · 상태 |
| `listComments` | `GET /user/comments/{postId}` | 댓글 스레드. 변경 로그는 `systemCode`로 가른다 |
| `listAlarms` (`listMentionAlarms` · `listTaskAlarms`) | `GET /user/alarms` | 멘션(§6.1.2) · 헤더 알림 종(§6.1.5). `receiverId`로 내 것만 남긴다 |
| `listEvents` | `GET /user/calendars/events` | 나의 일정. `userId`로 팀원 일정도 |
| `listDivisions` · `listEmployees` | `GET /user/divisions` · `/user/employees` | 부서 탭 · 부서원 명단 (팀 화면 §6.3) |
| `listParticipants` | `GET .../participants` | 담당자 후보 |
| `searchPosts` · `searchProjects` | `GET /user/search/*` | 검색 팔레트 (§6.4) |

**쓰기**

| 함수 | 엔드포인트 | 확인 방식 |
| --- | --- | --- |
| `setTaskStatus` · `setTaskEndDate` · `setTaskPriority` | `PATCH .../tasks/{id}/{필드}` | 지금 값을 누르고 → 고르면 즉시 저장 |
| `setTaskWorkers` | `PATCH .../tasks/{id}/worker` | 고르기 모달 → `확인` |
| `createTask` | `POST .../posts/projects/{id}/tasks` | 확인 문구 + 한 번 더 누르기 |
| `createComment` | `POST /user/comments/{postId}` | 즉시. Body는 `{contents}` 하나 — **답글 필드가 없다** |
| `markAlarmRead` · `markAllAlarmsRead` | `PATCH /user/alarms/read[/all]` | 즉시 |

**미사용**: 프로젝트 생성, 참여자 초대, 컬럼/뷰 생성, 캘린더 쓰기, 위키·드라이브, 삭제 계열
전부. flow에서 한다 (§13 Tier C).

**구현 시 반드시 지킬 3가지** (api-spec.md §10에서 관측된 함정)

1. 업무의 마감일·상태·진행률은 **평면 필드가 아니라 컬럼 배열**에 있을 수 있다. `columnSrno` 하드코딩 대신 `defaultColumnType`으로 찾는다.
2. 상태는 `"REQUEST"` 같은 enum이 아니라 **`optionSrno` 숫자 문자열**이다. 문자열 비교는 전부 실패한다.
3. 미설정 값은 `null`이 아니라 **빈 문자열 `""`**. `?? 기본값`이 동작하지 않으므로 falsy 체크로 통일한다.
